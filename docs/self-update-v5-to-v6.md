# 从 V5 原地更新到 V6：可行性评估

结论：**技术上能，而且不需要新写更新器**。V5 已经在用一套完整的
「检查清单 → 下载 APK → 拉起系统安装器」链路，发一个新包就会被它装上。

> 2026-10-27 定案：**V5 数据不对接 V6，全部舍弃**。原因见 §三。
> 这让升级从「要写迁移 + 可能要重试」变成「换入口 + 接更新器 + 发版」，
> 工作量从一天级别降到小时级别。

评估时间：2026-10-27。基于当前 `main`（`296258d`）。

---

## 一、已经具备的（不用开发）

| 能力 | 现状 | 位置 |
|---|---|---|
| 检查更新 | 拉 `update.json`（jsDelivr 多节点 → raw → GitHub API 兜底） | `lib/core/updater/services/app_update_service.dart` |
| 版本判定 | 语义化比较，主版本变化默认弹窗，支持强制更新 `minSupported` | `.../app_update_decider.dart` |
| 下载 | 多源回退 + sha256 + 大小校验，失败换源 | `.../app_update_launcher.dart`、`core/services/multi_source_downloader.dart` |
| 安装 | 下载到 cache → FileProvider → 系统安装器 | 同上 + `AndroidManifest.xml` 的 `REQUEST_INSTALL_PACKAGES`、`FileProvider` |
| 分发 | GitHub Releases（APK 超 20MB，不走 jsDelivr，已实测 403） | `update.json` 顶部注释有完整踩坑记录 |

也就是说：**用户当前的 5.5.26 就是这么装上去的**，这条路已经跑通。

## 二、四个硬条件（逐条核对）

| 条件 | 状态 | 说明 |
|---|---|---|
| 包名相同 | ✅ `com.noteapp.taskmaster` | 覆盖安装，不会并存两个 App |
| 签名相同 | ✅ 有 `android/key.properties`，keystore 在仓库外 | 必须用**同一把钥匙**构建，否则 `INSTALL_FAILED_UPDATE_INCOMPATIBLE` |
| 安装权限 | ✅ 已声明 + FileProvider 已配 | Android 8+ 首次会要求用户允许"安装未知应用" |
| versionCode 递增 | ⚠️ **需要改** | 见下 |

### versionCode 是唯一可能卡住安装的点

`pubspec.yaml` 现在是 `version: 5.5.26+0`，也就是 **versionCode = 0**。
Android 只认整数版本号，新包必须严格大于旧包才能覆盖。

发 V6 时把版本写成 `6.0.0+6000`（或任何 ≥1 的数）。这一步没做的话，
表现是"下载完成 → 安装失败 → 用户以为是包坏了"，而且错误提示不会说明原因。

> 无法从代码判断历史发布包用的是多少 —— 如果以前用 `--build-number` 覆盖过，
> 需要看一眼已发布 APK 的实际值。给一个明显大的数最稳。
## 三、数据：已决定不迁移

**2026-10-27 定案：V5 的数据全部舍弃，不做迁移。**

理由不在于「能不能迁」（结构差异其实很小，`tasks` 11 列同名、`recycled_tasks` 只差
`tag_ids`），而在于**迁了也没有意义**：

- V5 的数据模型里，积分、商城、刮刮乐、番茄钟记录都还在主库；
  V6 把它们全部移出到插件，主库只留任务 / 标签 / 设置。
- 就算把任务搬过去，用户升级后看到的仍然是一个**功能少了一大半**的应用
  （见 §七"功能倒退"）。这种情况下"保住旧任务"只是把割裂感往后挪了一步。
- 迁移代码是"一辈子只跑一次、但出错就无法挽回"的代码。既然不需要，就不要写。

### 落地时要知道的三件事

1. **旧库不主动删。** `v5_tasks.db` 留在应用私有目录里，V6 不读它。
   删它没有任何收益（几十 KB~几 MB），却会永久销毁用户数据。
   如果将来想清理，单独做一个"清除旧版本数据"的显式操作。
2. **升级前要先说清楚。** 更新说明里必须写：**升级后旧任务不会出现在 V6 里**。
   用户点下"更新"那一刻是唯一能告知的时机，事后再说等于狡辩。
3. **验收只需一条**：装 V6 → 首页是空列表 → 能正常新建任务。
   不需要"旧数据是否完整"这类验收项了。

## 四、两条线各自维护（2026-10-27 补充）

6.0.0 是 V5 **唯一一次**能看到 V6 的版本。之后两条更新线彻底分开：

| 渠道 | 清单 | 说明 |
|---|---|---|
| v5 | `update.json` | 冻结在 6.0.0，`minSupported` 保持 5.0.0（**不能提，提了就变强制**） |
| v6 | `update_v6.json` | V6 每次发版只改这份 |

V5 用户可以点「跳过此版本」不再被打扰 —— 这是引流能成立的前提：
**它是邀请，不是强制**。

实现与发布纪律见 `docs/update-channels.md`。

## 五、还缺的一块：V6 自己不会更新（发出去就绝版）

`lib/app/` 里没有任何 updater 引用 —— v6 外壳只负责界面。
如果新包的入口直接 `runApp(V6App())`，用户装上之后**再也收不到更新**。

补法很小：入口先建 `AppUpdateProvider`，用 `ChangeNotifierProvider.value` 提供，
再用 `AppUpdatePromptHost` 包住 `MainShell`（v5 的 `main.dart` 就是这么接的）。
`AppUpdatePromptHost` 只依赖 `context.read<AppUpdateProvider>()`，不需要整套 Provider 树。

## 六、实施顺序

| 步 | 内容 | 风险 |
|---|---|---|
| 1 | 把更新器接到 V6 外壳（`ChangeNotifierProvider.value` + `AppUpdatePromptHost`） | 低 |
| 2 | 主入口换成 V6（`main.dart` → `V6PreviewApp`），`pubspec` 改 `6.0.0+6000` | 中（见 §七） |
| 3 | 构建 release → 传 GitHub Release → **之后**才改 `update.json` | 中（签名 / 死链） |

第 3 步的顺序不能反：**先传包，再改清单**。清单先改成 6.0.0 而 APK 还没上传，
所有 V5 用户会立刻收到更新提示，点下去是死链 —— 而且他们不会再点第二次。

## 七、风险清单

- **签名换了就装不上**：`key.properties` 指向的必须是原来那把钥匙
  （`D:/Dev/keystore/`）。换了的话老用户只能卸载重装。
- **功能倒退**：V6 现在没有积分、商城、游戏、番茄钟、统计、桌面小组件。
  这些要等插件补。**升级前必须让用户知道这一点**，否则"更新完怎么什么都没了"
  比"数据没迁"更让人恼火。
- **降级不可能**：Android 不允许 versionCode 回退。要回 V5 只能卸载重装，
  而且 V5 库虽然还在，重装 V5 后它能读回来 —— 这是"不删旧库"唯一的实际价值。
- **用户不会主动点更新**：V5 已有后台检查 + 通知栏提醒，沿用即可。

## 八、已定/待定

| 事项 | 结论 |
|---|---|
| V5 数据迁移 | **不做**（2026-10-27 定） |
| 旧库是否删除 | 不删（无收益，且是唯一退路） |
| V6 包是否保留 V5 界面入口 | 建议不保留，两套代码都要维护 |
| 是否接受功能倒退后再逐步补插件 | **待确认** —— 这是唯一影响"现在发不发"的问题 |
