# 两个 App 的双向引流（5.x ↔ 6.x）

> 2026-10-30 定案并落地。V5 5.5.27 与 V6 6.0.1 起生效。

## 为什么要两个 App

6.x 换了包名（`com.noteapp.taskmaster.v6`），因为用户要的是"通过 V5 下载 V6，**V5 还留着**"。
包名相同的话 Android 只会当成同一 App 的新版本覆盖安装，不可能并存。

代价：**它俩是独立的两套数据**，V5 的任务和积分不会带过来。
好处：随时能退回 V5，不存在"升上去回不来"。

## 两条入口，各自独立

| 方向 | 在哪 | 指向 | 怎么走 |
|---|---|---|---|
| V5 → 6.x | 设置 → 版本更新 → 「任务管家 6.0.0（新版）」卡 | 写死在 `lib/core/config/legacy_v6_link.dart` | 更新器同一条管道：下载 → 校验 sha256 → 拉起系统安装器 |
| 6.x → V5 | 设置 → 关于 → 「下载旧版（V5）」 | 读 `note_study` 的 `update.json`，读不到用 `legacy_v5_link.dart` 兜底 | 同上 |

（V5 5.5.29 / V6 6.0.3 起）

## 关键：入口读的是**对方的清单**，不是写死的版本

写死版本号有两个后果，都很烦：

1. 每改一次就要**两边各发一版**（改 A 的入口 → A 发版 → B 里的兜底指向 A 的旧版 → B 也发版……）
2. 装了之后拿到的永远是"上一次发版时对方的版本"，不是最新的

现在两个入口都是：**去拉对方仓库的 `update.json`**，用里面的 `latest.version`
和 `<platform>-<abi>` 那一项（url / sha256 / sizeBytes）。

- 仍然校验 sha256（清单里本来就写了每个包的摘要）
- 仍然按 ABI 选包（arm64 只下 21–23MB，不是 62MB 整包）
- **读不到才回落**写死的那份 —— 入口不能因为一次网络失败就消失
- 读清单是异步的：卡片先按已知版本画出来，读到了再把版本号刷新

于是：V6 发 6.0.4、6.0.5……**V5 不用动**，用户点进去拿到的就是那个新版。
反过来也一样。这条线上不再有"发版连锁"。

**唯一不能共用的是那份清单本身**：`update.json` 只回答"我这个 App 有没有
新版本"。曾经试过让 V5 的清单直接指向 6.0.0，一天内就拆了 —— V5 再也没法
发自己的版本（用户会看到"最新版是 6.0.0"，那是另一个 App），版本号语义也乱。
所以是"各读各的清单，只是读对方那份"。

## 下载源顺序

两个方向都是：**Gitee → GitHub 直连 → ghfast / gh-proxy 两个公共代理**。

- Gitee 是国内唯一能稳定下大文件的那条腿（GitHub 的 `objects.githubusercontent.com` 常年不通）
- 公共代理只是兜底，随时会挂，所以排在后面
- 无论走哪条源，装之前都校验 `sha256` —— 代理不可信，但摘要能兜住

## CDN 缓存这件事（5.5.26 用户的最后一道坎）

jsDelivr 对 `@branch` 的解析结果有自己的缓存，最长 12 小时，`purge` 刷不掉 gcore 节点。

5.5.26 的更新器是"**第一个成功就用**"，撞上 gcore 的旧清单就停在那儿 —— 清单改了也白改。
这就是 5.5.27 要修它、并且只能靠"用户先升到 5.5.27"才能彻底解决的问题。

5.5.27 起改成**并发拉所有源、按 `updatedAt` 挑最新**。实测（2026-10-30 12:44）：

```
gcore        → 5.5.26   ← 旧缓存
fastly       → 6.0.0    ← 更旧的缓存，但版本号更大
testingcf    → 6.0.0
cdn.jsdelivr → 6.0.0
raw          → 5.5.27   ← 真的那个
```

5.5.27 客户端给出的结论是"已是最新 5.5.27"，**没有**被那份 6.0.0 带偏
（按老逻辑会弹"发现新版本 6.0.0"，而那是另一个 App 的版本号）。

## 维护清单

**日常发版**（6.0.4、5.5.30……）：什么都不用做。两个入口自己会读到对方的最新版。
清单由各自的 `publish_release.ps1` 生成，里面本来就带分架构的 url / sha256 / 体积。

**改入口本身**（比如换兜底版本、改文案）：

1. 兜底常量（`legacy_*_link.dart`）要与清单里的 `sha256` / `sizeBytes` 一致，
   否则"清单读不到"的那条路上校验必挂
2. 兜底版本发出去之后**不要再重发**，否则那个版本的校验会失效
3. 入口改完两边各发一版是正常的 —— 但**只为入口本身发版，不再为"对方发新版"发版**

**清单要改时**：刷 jsDelivr 缓存，但别指望立刻生效（见上）。
