# 多人与多 agent 协作

> 最后更新：2026-11-01

前提：**真人只做小改动，主体是多平台 AI agent；各平台的上下文/记忆/规则文件不共享。**
所以仓库文档是唯一共享记忆，任务文件是唯一交接凭证，聊天上下文不算数。

## 1. 角色（帽子，不是人）

一个小团队不需要层级，但需要四顶帽子。一个人/一个 agent 可以同时戴多顶，
但**必须在自己任务文件里写明戴了哪几顶**。

| 角色 | 负责 | 不该做 |
|---|---|---|
| 协调者 | 定范围、拆任务、裁决接口冲突、决定“什么时候算完成” | 不亲自改所有代码；不和实现者同一人做不可逆变更的最终验收 |
| 实现者 | 按任务文件改代码、写测试、给出证据 | 不擅自扩大范围；不跨文件所有权改别人的文件 |
| 核查者 | 独立复现、对账、反向测试、检查文档与代码一致 | 不复述实现者的结论；不只看“测试绿了” |
| 发布者 | 版本号、构建、签名、上传、清单、CDN | 不在未签收时推送；不先改清单后传包 |

**小改动例外**：只改文案/单文件 UI/注释，可以由一个人全包；但数据、契约、
发布链路、安全相关改动**不允许**实现者自己当最终核查者。

## 2. 任务文件（claim）

每个非平凡任务在 `docs/ai/work/<YYYY-MM-DD>-<英文短名>.md` 建一个文件，模板见
`docs/ai/templates/task-claim.md`。它是**唯一交接凭证**，至少包含：

- 任务 id / 标题 / 协调者 / 实现者 / 核查者
- 范围（要做什么、明确不做什么）
- 涉及文件/目录（用来避免两个人同时改同一处）
- 依赖（前置任务、需要谁裁决）
- 验收口径（指向 `docs/acceptance/` 或本文件条目）
- 状态（`claimed` / `in_progress` / `blocked` / `review` / `done`）
- 交接区（当前进度、下一步、已知坑）

规则：

- **开工前先建 claim 文件**；同一天同主题只允许一个 owner。
- 只改自己的任务文件；不要编辑别人的 claim（需要协调时在对话里说，由协调者改）。
- 任务结束后文件保留，不删；它是“当时怎么做的”记录，不是临时草稿。
- 真人小改动可以跳过 claim 文件，但仍要在提交信息里写清范围。

## 3. 文件所有权

按目录分，不按“谁先打开”分。默认 owner 如下（角色可重叠）：

| 目录/文件 | Owner 帽子 |
|---|---|
| `lib/core/data/` | 数据 |
| `lib/core/plugin/`、`lib/core/extension/` | 平台 |
| `lib/core/updater/`、`lib/core/services/` | 发布/网络 |
| `lib/core/backup/`、`lib/core/field/` | 数据/平台 |
| `lib/app/shell/`、`lib/app/pages/`、`lib/app/widgets/` | 界面 |
| `lib/app/state/`、`lib/app/data/` | 应用装配 |
| `plugins/src/`、`plugins/packages/`、`assets/plugins/` | 插件 |
| `tool/`、`pubspec.yaml`、`update.json` | 发布 |
| `docs/` | 文档 |

规则：

- **不跨 owner 直接改**。需要改别人的文件：先在任务文件里写“我要改 X，因为 Y”，
  由协调者确认；紧急修复可以事后补记录，但必须补。
- 同目录多人并行时，按**文件**再切细：一个文件同一时间只有一个 owner。
- 公共契约文件（`plugin_manifest.dart`、`plugin_bridge.dart`、`destinations.dart`、
  `v6_schema.dart`、`extension_*`、`SettingsKeys`）改动视为**接口变更**，走 §4。
- 格式化/重命名导致的大 diff 单独提交，不和功能改动混在一起，方便回退。

## 4. 接口变更协议

以下任一变化必须**先写决策记录，再改代码**：

- 插件 manifest 字段、权限名、bridge 方法/参数/返回、插槽/钩子 id、契约版本
- 数据库表/列/迁移语义、设置键名、备份格式
- 入口清单 `AppDestination`、首页模式编码、货币接口
- 发布清单 `update.json` 结构、插件索引结构

流程：

1. 在 `docs/decisions.md` 追加一条：改什么、为什么、否掉了什么、影响谁。
2. 同步 `docs/plugin-contract.md` / `docs/update-channels.md` / `docs/main-package.md`
   中受影响的部分（只改唯一源，别复制）。
3. 判断契约版本是否 +1：变了插件可见的接口 → +1；只加不破坏的字段 → 可不升，
   但要在文档写明“老插件不读它，照旧工作”。
4. 在任务文件里 @ 相关 owner；实现者不能自己决定“这个变更不用通知别人”。

**没有决策记录的接口变更，核查者可以直接打回。**

## 5. 交接（上下文不共享）

暂停/换人/换平台时，在任务文件的“交接区”写清：

- 已完成什么（对应文件/测试）
- 下一步具体做什么（不要写“继续完善”）
- 已知坑/失败尝试（避免下一个人重试同一个错）
- 未验证的东西（真机、边界、未复现 bug）
- 当前分支/提交（如有）

接手的 agent 先读：`AGENTS.md` → `docs/ai/README.md` → `docs/INDEX.md` →
`docs/decisions.md` → 任务文件 → 相关源码。**不要凭“上一个 agent 说完成了”就继续。**

## 6. 证据规则（防止“看起来对”）

这条来自项目里真实发生过的损失：凭空编造 bug/脚本、把“应该验证”写成“已经验证”、
用旧截图坐标点击、用管道把测试失败盖成 0。

- 任何“我发现/已修复/已验证”的陈述，必须能指到**文件:行号**或**命令真实输出**。
  指不出就是没验证。
- 任何“请执行 X”的指令，发出前先确认 X 存在（`ls`/`test -f`）。
- “应该验证”只能写成待办，**不能写成已通过的发现**。
- 读别人的输出要读完整行/完整表头；不要拿半行结论下判断。
- 评价过去的事，先查时序（`git log -S` / `git show <commit>:<file>`），
  不要拿后来的版本倒推。
- 测试要证明“能抓住它要抓的 bug”：写完先对着 bug 跑一次（反向测试），
  否则可能是假绿。
- 断言成对：该有的还在 + 不该有的没了；场景被跳过 = 失败，不是通过。

## 7. 沟通模板（短）

**任务开始**

```
任务：<一句话>
范围：只改 <文件/功能>；不改 <明确排除>
验收：<可观察条件 / 验收清单编号>
风险：<数据/契约/发布/真机>
```

**阻塞**

```
卡在：<现象>
已排除：<做过什么、结果>
需要：<谁裁决/提供什么>
```

**交付**

```
改了什么：<1-3 条>
证据：<测试名/命令输出/截图>
没验证：<真机/边界/未复现>
下一步：<具体动作>
```

## 8. 冲突处理

- 两个任务改了同一文件：后发现的停手，由协调者合并；不要互相覆盖。
- 两个结论相反：以可复现证据为准；不能复现的结论标“假设”，不是事实。
- 接口/数据冲突：协调者裁决并写决策记录；裁决后必须通知**实现者和文档 owner**，
  只通知一方会导致“代码按旧裁决写对了却被判失败”。
- 用户明确说“先讨论定案再动代码”时，带问号的消息是征求意见，不是下指令。

## 9. 不要做的事

- 不要假设其他 agent 记得你上一轮说过什么。
- 不要把平台本地记忆/规则当成项目规则。
- 不要为了让任务“看起来完成”而降低验收标准。
- 不要在未签收时推送；不要先改清单后传包。
- 不要在同一轮里既改功能又做大范围格式化/重命名。
