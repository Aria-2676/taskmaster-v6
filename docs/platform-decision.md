## 0. 这份文件要解决什么

上一次换栈（v5 → v6/RN）被叫停，**根本原因不是技术选错，而是"要不要做"和"要做成什么样"都没对齐就开始做**：

所以本文的顺序被刻意固定为：**先钉目标 → 再列能力 → 再比方案 → 最后才选栈**。

## 4. 两方案的诚实账

| | C：Flutter + WebView 插件 | D：RN + Re.Pack 分包 |
|---|---|---|
| 主体重写量 | **0 行**（33747 行 Flutter 原样保留） | **3.4 万行 Dart → TS**；v6 存档已搬约 10%（数据层 + 6 屏，缺 Tasks/Detail/Edit/Tags/Points 五个核心屏，也就是最难的 5579 行任务模块） |
| 需新建的基础设施 | WebView 宿主 + JS bridge + 统一设计系统 + 插件管理器（**已有约 60%**：`GameAssetServer` / `webview_flutter` / zip+sha256+多源下载 / `GameModuleService` 的完整生命周期） | Re.Pack 替换 Metro + `ScriptManager` 解析器 + remote chunk 清单 + 契约版本矩阵（这些仓库里**没有**任何现成件） |
| 工期（业余口径，粗估） | 2~3 个月到"能用"，可分段停 | 4~6 个月到"能用"，中途难停（换了构建链就回不去了） |
| 技术风险 | 低：WebView / zip / 下载 / 原子替换全是成熟件，且项目已在跑 | 中：Re.Pack 由 Callstack 维护、方案成熟，但**替换 Metro 会动整个构建链**，出问题的面更大 |
| 长期维护 | Flutter 升级平稳；成本在"守设计系统" | RN 每年大版本 + 依赖碎片；一人维护成本显著更高 |
| 观感 | 插件页打折 | 接近原生 |
| 系统能力 | 插件完全拿不到 | 可用已内置的原生模块 |

> 关于 D 的事实依据：Re.Pack 的 remote chunk 机制**就是把功能代码不打进包、运行时从 CDN 按需下载**，且 chunk 内是原生 RN 组件（`React.lazy` + `dynamic import` + `ScriptManager` 解析）。这确实是移动端少见的"按需装 + 原生观感"同时成立的方案。
> 附带限制（官方文档明示）：chunk 是**可执行代码**，只能来自自有且可信的来源；iOS/商店场景下用代码分包下发"整块新功能"可能违反商店条款 —— 本项目不走商店，不受此限。

## 5. 决策判据：真正分叉的只有两条

1. **#10**：插件页面能不能"看起来是主包的一部分"？
   - 用户的参照物是现存的**小游戏页**（`game_host_page.dart`，最省事的 WebView 容器）——
     那是最差样本，不代表"用心做的 WebView"的上限。判断需要看样机或对照小程序。
2. **#13**：插件能不能复用主包的 UI 组件与数据层？
   - **这一条比 #10 更根本**：它决定插件是"亲生的"还是"外挂的"。
   - C 里，每个插件都要自带一套 HTML/CSS/JS，与主包只通过 bridge 通信，
     风格一致**靠人守纪律**；主题切换、组件升级、空状态插画都要在两边各做一遍。
   - D 里，插件 chunk 与主包在同一 JS 上下文，可直接 import 主包组件库与数据层，
     风格一致**由结构保证**。
   - 对"平台"而言，这是本质差别：**C 是"主包 + 一堆外挂页面"，D 是"一个长得出东西的整体"。**

> 备注：若最终判定"暂不做插件、只要不发版就能加功能"，**Shorebird** 是省事得多的替代（Dart 代码补丁，原生观感，$0 免费档）。但它**全局推送**，所有用户都会拿到全部代码，因此**不满足"按需装、不装不占"**。当作退路记录，不作为主选。

## 6. 分级模型：「基础版内置 + 增强版插件」

用户的表述（我的理解，待确认）：

- 标签、回收站、数据备份 —— **基础能力**，随主包内置，最小可用
- 「标签系统」「数据备份系统」—— **拓展**，作为插件（完整版：层级/颜色/批量、定时备份/多版本/导入导出）

这**不是两个功能，是同一个功能的两档实现**：基础版在主包，增强版是插件；装上接管该功能的界面与能力，卸下自动回退基础版。

→ 这正是「父模块（优先级高于主模块）」的真正含义：**不是外来代码覆盖核心，而是同一契约下的增强实现**。
→ 成立前提：契约冻结 + 基础实现必须永远存在（槽位模型，见 §8 第 4 条）。
→ 在 D 里这天然成立（同一 JS 上下文 + 复用主包组件）；在 C 里要靠在 bridge 上人为造一套并行实现。

### 7.5 两级扩展位（本轮新增的关键结论）

用户要求：**主界面里的局部内容（积分显示、日历条）也要能被插件改动**，不只是整页替换。
这比"页面级插件"深一层，必须分成两级处理。

| 级别 | 插件提供什么 | 谁负责渲染 | 典型位置 |
|---|---|---|---|
| **页面级** | 一整个页面（WebView 承载） | 插件 | 统计、番茄钟、商城、日历视图 |
| **区域级（插槽）** | **只提供数据 / 配置** | **主包渲染** | 顶栏日期格式、积分徽章、日历条标记、任务卡片附加行 |

**已定档：A 档 —— 只改数据。** 插件能决定"显示什么、点了去哪"，不能改字体/圆角/间距/颜色。
未来的插槽（按出现顺序）：顶栏日期 → 积分徽章 → 日历条标记 → 任务卡片附加行。

**为什么区域级不能塞 WebView**：一个 40dp 高的 WebView 要独立进程/几十 MB 内存，
白屏抖动在这么小的区域里极其显眼，字体与原生不一致，无障碍失效 —— 为了显示一个数字不值。

**所以区域级插槽 = 数据插槽**：插件说"显示什么、点了去哪"，主包负责画，观感 100% 一致、零额外开销。

**成本**：主包必须在 UI 层预留插槽。好消息是这几个部件**本来就已是独立 widget**
（`task_calendar_widget` / `tag_filter_widget` / `task_card_widget` / `top_slide_menu_widget`），
改造成插槽的成本低于从零设计。坏消息是主包从此变复杂，每个插槽都是一份契约。

**边界**：区域级插槽只允许改"内容"，不允许改"皮"（字体、圆角、间距仍由主包定）。

## 10. 已达成的共识

- 仓库内旧文档不作数，**事实以代码为准**
- 插件作者只有官方，不需要第三方 SDK 体系
- 扩展位分三级：页面级（WebView）/ 区域级（数据插槽，A 档）/ 服务级（替换实现）
- "父模块"= **同一契约下的另一种实现**，不是猴子补丁式改写
- 功能分两档：基础版内置、增强版为插件，卸载自动回退基础版
- 兼容性用**契约版本**判，不用 app 版本号
- 包体不是首要目标，首装极简与可扩展性才是
- 系统能力（通知/后台/小组件）必须常驻主包，与是否装插件无关
- **货币：框架在主包，实现全在插件**（能量 / 积分），一个时刻只一个生效
- 插件之间允许**软依赖**（商城依赖"存在生效货币"），缺了就引导，不做依赖解析
- 主题走 `theme.json` 资源热更（已是现状，零改造）
- 小游戏已经是"插件"形态，但**它的观感是下限样本，不作为标准**
