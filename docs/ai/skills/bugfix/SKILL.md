# Bug 修复

> 最后更新：2026-11-01

## 什么时候用

- 用户报告的现象、回归、崩溃、数据不一致
- 测试/真机发现的行为错误

**不适用于**：新功能（`feature-dev`）、插件包问题（`plugin-dev`）、发版（`release`）。

## 步骤

1. **读上下文**：`docs/INDEX.md`（已证伪断言）、`docs/decisions.md`（既有设计）、
   相关源码与测试。
2. **复现/定位**：
   - 尽量用最小步骤复现；记录设备/版本/入口。
   - 先判断是“缺陷”还是“有意的分层/历史包袱”；不要一上来就重构。
   - 查调用方，不要凭结构推断“死代码”。
3. **给出机制层面的因果**：指到文件:行号或命令输出。
   - 指不出 → 只能算“怀疑”，不是“发现”。
   - 不要编造 bug/脚本；发“请执行 X”前先确认 X 存在。
4. **先写会红的测试**（单元/widget/DB/脚本），证明断言能抓住这个 bug。
5. **修**：最小改动；不要顺手改无关代码。
   - 如果原因无法完全消除，加一层“即使原因仍在也兜得住”的保险，
     并给保险写自动化测试。
6. **反向验证**：把修复临时改回去，确认测试变红；再恢复。
7. **自检**：`flutter analyze lib` + 全量测试；必要时真机/模拟器复验。
8. **验收清单**：写明“修之前现象 / 修之后可观察结果 / 回归项 / 未验证项”。
9. **本地提交**：提交信息写根因与修复方式；**不推送**，等签收。

## 不可复现的 bug

“再试一次没出现”不是验收标准。二选一（最好两者都做）：

- **机制证明**：用事件序列/日志/数据证明旧代码为什么错。
- **保险**：加兜底（如 `PendingDeleteGuard`），且兜底路径有自动化测试。

交付说明必须写明“哪一部分是机制证明、哪一部分是保险、哪一部分仍未验证”。

## 硬规则

- 不要用文案盖住原始错误；能拿到异常就露原文（截断即可）。
- 不要用 `try/catch` 吞掉错误后继续，除非明确写了“失败也继续”的最坏结果与自愈路径。
- 不要为了通过测试改断言；断言要成对（该有的还在 + 不该有的没了）。
- 场景被跳过 = 失败，不是通过；扫描目标缺失 = 失败。
- 平台层问题（弹层热区、键盘、Insets、通知权限）widget test 测不出，
  必须真机/模拟器；验收里单独标“需真机”。

## 输出

- 修复代码 + 反向测试
- 根因说明（文件:行号/命令输出）
- 验收清单（含未验证项）
