# 任务 · 全局搜索（6.8）

> 日期：2026-11-19 ｜ 状态：review（三步都写完，日记待真机签收）
> 协调者：用户 ｜ 实现者：小鱼 ｜ 核查者：用户

## 目标

一个输入框，一次搜出任务、计划、备忘、清单、日记里的东西，点结果直接跳到那条。
出口条件（路线图 6.8）："一次搜索跨模式出结果；备忘→任务→计划可跳转"。

## 已拍板（2026-11-19）

- 入口：**只放侧边栏**（顶栏太挤）
- 排布：**按类型分组**
- 已完成任务：**搜，排后面并标灰**

## 三处取舍的原始分析（留档）

### ① 入口放哪

| 方案 | 优点 | 代价 |
|---|---|---|
| **A. 顶栏放大镜**（推荐） | 高频操作两步可达；不占底栏 | 顶栏已经有 `+`、货币、☰，再加一个会挤 |
| B. 侧边栏加「搜索」 | 零挤压 | 要找三次：☰ → 搜索 → 输入 |
| C. 两者都加 | 都方便 | 两个入口指向同一页，维护上没问题，只是多写一行 |

倾向 **A + B（即 C）**：搜索页只有一个，入口多一个不增加维护成本。
顶栏那个在"今日任务"和任务列表页出现（首页被插件占时不出现，避免和插件的顶栏打架）。

### ② 结果怎么排

| 方案 | 效果 |
|---|---|
| **按类型分组**（推荐） | 「任务 3」「计划 1」「备忘 2」分段，用户知道自己搜到了什么类型的东西，可预期 |
| 混排按相关度 | 需要给每类算分，跨插件根本算不准（插件只返回它觉得相关的），结果是"莫名其妙排第一" |

倾向**分组**。理由：跨插件的相关度没有共同标尺，硬排只会更乱。

### ③ 搜多深

| 项 | 建议 | 理由 |
|---|---|---|
| 已完成任务 | **搜**，但排在未完成之后，并标灰 | 用户找"上周做过的那个"是常见诉求 |
| 回收站 | 不搜 | 那是"已删除"，不该出现在正常搜索里，容易误以为还在 |
| 日记正文 | 搜 | 日记的价值就在正文 |
| 插件数据 | 走插件自己实现（见下） | 主包不碰插件的表（`decisions` 已有约束） |

## 数据来源与查询

| 类型 | 谁负责 | 怎么查 |
|---|---|---|
| 任务 | 主包 | SQL：`title LIKE ? OR description LIKE ?`，limit 50 |
| 计划 / 备忘 / 清单 / 日记 | 各自插件 | 新增查询方法 `<domain>.search` |

统一结果结构（插件返回，主包补 `source`）：

```json
{
  "items": [
    { "id": 7, "title": "Reading", "subtitle": "进行中 · 33%" }
  ]
}
```

- `id` 用于跳转
- `subtitle` 由插件决定（它最清楚该显示什么）
- 主包只负责"展示 + 点击跳转"

查询方法名：`plan.search` / `memo.search` / `list.search` / `journal.search`。
参数统一 `{ keyword, limit }`，与现有 `plan.list` 同一套 `host.onQuery` 机制，**不新造协议**。

## 跳转

| 类型 | 动作 |
|---|---|
| 任务 | 打开任务编辑页（主包内部） |
| 计划 | `openWith: {kind:'plan', id}`（已实现，见 2026-11-17 的任务） |
| 备忘 | `openWith: {kind:'memo', id}` —— 备忘没有详情页，插件需要滚动到那条并高亮 |
| 清单 | `openWith: {kind:'list', id}` —— 直接进该清单内页 |
| 日记 | `openWith: {kind:'journal', id}` —— 滚动到那篇 |

**前置已完成**：带参数打开在 2026-11-17 打通（`plugin-contract.md` §5.1）。

## 降级与超时

- 只搜**已装且启用**的插件；没装的不参与，不报错
- 每个插件 2 秒超时（复用 `PluginQueryHost.timeout`），超时的那组不显示，底部一行小字
  「部分模式未接入」
- 输入防抖 300ms；上一次请求未回来时不叠加，直接丢掉旧的（搜索结果对时效敏感）

## 明确不做

- 分词 / 拼音首字母 / 模糊匹配排序：数据量在几千条以内，`LIKE` 够用；做了反而不可预期
- 搜索历史与联想：先能用
- 跨插件联合打分：见 ②
- 索引表 / FTS5：等真的有性能问题再说，现在没有证据

## 分步（每步可独立验收）

1. **主包侧**：任务搜索 SQL + 搜索页 + 顶栏入口。不依赖任何插件，装不装插件都能用。
2. **计划 + 备忘**：这两个已经在今日页跑通了查询链路，验证面最小。
3. **清单 + 日记**：补剩下的两个。

## 风险

- **契约**：新增 `*.search` 方法，需要写进 `plugin-contract.md`；老插件不实现就不参与搜索，
  不影响它能打开
- **性能**：5 个 WebView 同时被查询 —— 离屏宿主已经能同时托管多个，但"同时 5 个"没测过
- **真机**：防抖和输入法组合下的手感只能真机验
