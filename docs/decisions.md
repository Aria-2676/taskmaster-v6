# 设计决策与取舍

本文件只记**非显然的取舍与踩过的坑**，供以后回溯「当初为什么这么定」。
**规则本身在 `.trae/rules/`（同名主题的规则卡）**，这里不重复规则内容。

> 为什么把「规则」和「决策记录」分开？此前一份 370 行的「开发规范」把两者混在一起，
> 结果同一批规则被抄成了三份（详版 / IDE 规则卡 / CLAUDE.md），靠人肉同步，
> 已经漏改过一次。现在规则唯一保存在 `.trae/rules/`，原因记在这里。

## 为什么 core 不能依赖 modules

core 是所有模块的地基。一旦它反向依赖某个模块，就无法被单独测试与复用，
且模块增删会波及全项目。代价是 core 需要通用能力时得自己定义异常与接口
（如 `ZipExtractorException`、`FileDownloadException`），由各模块在自己的
边界处转换成自己的异常类型——换来的是重构底层时调用方的 `catch` 种类不变。

## 为什么外部数据解析要 fail-soft

清单（`update.json`、游戏 `manifest.json`）来自外网，一个字段笔误不该让整个功能瘫痪。
所以：顶层结构不对 → 抛（这是程序错误，必须暴露）；
单个字段非法 → 只丢该字段，其余照常可用。

## 为什么统计要节流

统计走本地 `SharedPreferences`，每次 `report` 都是「读整份缓存 → 追加 → 重写」，
上限 2000 条。游戏局内每次得分都上报会造成写放大。
故局内节流为 ≥5 秒一次；但**回合结束的最终分数必须无条件下沉**——
否则会在 `SharedPreferences` 写入节流后丢最高分。

## 为什么资源包用整数 build 而非版本号

小游戏/资源包一天可能重打十几次。语义化版本会迅速撞号，且「同版本不同内容」
会让缓存判断失效。单调递增整数最不容易出错——发布时只增不减，绝不回退。

## 为什么资源热更要「原子替换」

资源热更不弹窗、不安装，用户看不到过程，所以**绝不能留下半旧半新的目录**——
那会让功能时好时坏且极难排查。流程是
下载到临时目录 → 先校验 sha256 再解压 → 解压到临时目录 →
旧目录改名 `.bak-<stamp>` → 新目录改名正式 → 删备份。
两次 `rename` 在同一分区是原子操作；晋升失败会把备份改名回去。
**只有成功之后才写回 `assetBuild`**，否则失败时构建号被推进，该资源包会被永久跳过。

## 为什么大文件不走 cdn.jsdelivr.net

`cdn.jsdelivr.net` 对 `.zip` / `.apk` 会 301 跳转到 `raw.githubusercontent.com`，
该域名在国内经常被 reset，表现为「下载到一半失败」或「校验不过」。
所以大文件首选 `gcore.jsdelivr.net`，回退 `testingcf` → 源站。
（也曾因多镜像缓存不一致导致游戏包校验失败，故每次拉取都要按顺序试。）

## 为什么 APK 自更新对签名这么敏感

Android 要求更新包与已安装包同签名，否则 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`，
用户只能卸载重装并丢数据。密钥库因此**刻意放在仓库外**（仓库是公开的），
且口令**不由 AI 生成或记录**——它不该进对话日志，丢了也不可恢复。

### 口令外露时的处置：把密钥库降级为「本机测试用」

密钥库一旦用「已经出现在对话记录/日志里的口令」生成，它就不再是干净的密钥。
正确的分层是：

| 用途 | 该用哪个密钥库 |
|---|---|
| 本机调试、验证构建链路 | 现有这个（口令已外露，无所谓） |
| 对外分发、给真实用户更新 | **另生成一个**，口令亲手输入且从未外传 |

关键判断依据不是「口令强不强」，而是**口令有没有离开过你的机器**。
`setup_android_keystore_auto.ps1` 因此被标注为「仅本机测试用」。

### 为什么备份脚本会打包口令

密钥库和口令是**一对**：只备份 `.jks` 而不备份口令 = 没备份（口令无法从密钥库反推）。
所以 `backup_android_keystore.ps1` 把两者打进同一个 zip，并附 `README.txt` 说明恢复步骤。

代价是这个 zip 的敏感度**等同于房子的钥匙**：绝不入库、绝不放公开云盘，
只放密码管理器附件 / 加密 U 盘 / 私密保管库。`.gitignore` 里的排除规则
（`**/taskmaster-signing-*.zip`）是**纵深防御**——真正的密钥库本就在仓库外。

### keytool 在 PowerShell 5.1 下的 stderr 陷阱

`keytool -v` 把进度横幅打到 stderr。PowerShell 5.1 会把**原生 stderr 升级成
`NativeCommandError`**，脚本顶层 `$ErrorActionPreference='Stop'` 会因此在
**写完密钥库、但还没写 `key.properties`** 的那一刻中断——表现为「脚本失败但
.jks 已经生成」，极易误判成 keytool 出错。

处置：在调用点降级 `$ErrorActionPreference` 并用退出码判定成败
（`setup_android_keystore_auto.ps1` 走 `cmd /c ... 2>nul` 把 stderr 交给 OS 丢弃；
`setup_android_keystore.ps1` 局部降级 preference）。改这段时别改回去。

## 为什么现在有 `CLAUDE.md`、`.trae/rules/`、本文件三份

它们**不是三份规范**，而是三种不同职责：

| 文件 | 职责 |
|---|---|
| `.trae/rules/rule-*.md` | **唯一的规则来源**，IDE 自动加载 |
| `CLAUDE.md` | AI 的**操作手册**（项目事实、验证命令、环境坑、纪律），不复述规则 |
| 本文件 | **为什么**：取舍与踩坑记录，不写规则 |

改规则只改 `.trae/rules/`；**不要让规则在本文件或 `CLAUDE.md` 里再出现一次**。

各卡开头标了「适用：…」，`.trae/rules/README.md` 是「主题 → 文件」的薄索引——
它们的作用是让 AI 干活时**知道该读哪一张，而不是把七张全读一遍**。
索引只放定位信息，不放条文，所以它不是第四个副本。

### ⚠️ 关于 Trae 自动生成的项目记忆

Trae IDE 会为工作区自动维护一份项目记忆（`~/.trae-cn/memory/projects/<工作区>/project_memory.md`），
内容是它自己归纳的规则摘要，AI 会读到它。**这份文件不归仓库管、也无法完全关闭**，
且实测确实残留过已删除的条文（如「缩进 4 空格」、`V5.0.x` 旧提交格式）。
对策有两条：① 改完 `.trae/rules/` 顺手核查它；② **规则引用只写主题名，不写 `rule-N` 编号**，
让规则卡即使增删重排也不会留下悬空编号。

同理，`CLAUDE.md` 里也只是**指向** `.trae/rules/`，不缓存条文。

# 2026-10-22 ｜ 平台化改造的六个关键取舍

> 完整论证见 `docs/platform-decision.md`、`docs/main-package.md`、`docs/plugin-contract.md`。
> 这里只记「为什么这么定」和「当时否掉了什么」。

## 为什么不换栈（第四次才定下来）

讨论中出现过三种方案：A 全内置+开关、C Flutter+WebView 插件、D RN+Re.Pack 分包。

关键事实：**RN 的 Re.Pack 确实能同时做到"功能代码按需下载"与"原生控件观感"**
（`React.lazy` + `dynamic import` + `ScriptManager` 解析远端 chunk），这是移动端很少见的组合。
所以"换栈"这次不是没有理由。

但把 12 条能力摊开逐条对照后发现：**C 与 D 只有两项不同——观感、以及"插件能否复用主包 UI 组件"**，
其余十一项等价（包括"系统能力"这一项，两者都被"宿主已内置的原生能力"卡住上限）。

而 C 的代价是 0 行重写、保住 3.47 万行与 838 个既有测试；D 的代价是重写全部代码 + Re.Pack 替换 Metro
+ 一人长期维护 RN 大版本。**用全量重写去换两项能力，对单人项目不划算。**

前提是"刮刮乐接受手感下降"——这是 C 唯一被触摸延迟严重伤害的场景，用户已同意可降级甚至舍弃。

## 为什么用 WebView 而不是"让 Flutter 动态加载代码"

Flutter release 把 Dart AOT 成机器码，**没有运行时加载代码的机制**（`deferred` 仅 web 有效，AOT 无反射）。
这不是"难"，是"不存在"。所以"插件"只能是**资源 + 脚本**，载体只能是 WebView。
小游戏中心已经是这个形态（zip + `GameAssetServer` + `webview_controller`），是现成的验证。

## 为什么扩展位要分三级（原本只想到一级）

一开始只考虑"一个插件 = 一个整页"。用户提出"主界面里的积分显示、日历条也要能被插件改"，
这才发现局部区域与整页是两件事：

- **页面级**：整页交给 WebView
- **区域级（插槽）**：40dp 高的位置不可能塞 WebView（几十 MB 内存、白屏在小区块里极显眼、
  字体与原生不一致、无障碍失效），所以只能"插件供数据、主包渲染"
- **服务级**：替换某个服务实现（如货币的产出规则）。风险最高，因为改的是数据语义

区域级定为 **A 档——只许改数据，不许改皮**（字体/圆角/间距/颜色归主包）。

## 为什么货币是"框架在主包、实现全在插件"

最初的判断是"积分被任务、商城、刮刮乐三处依赖，所以账本必须留主包"。
但用户指出"能量和积分是两套货币，核心是同一套系统"——有两套实现，账本就不该在主包。

于是主包只留 `CurrencyRegistry` + `activeCurrency` + 统一接口，**主包不知道有"能量"或"积分"这种东西**。
代价是 `tasks.reward_points` / `is_deducted` 必须从主包表里移除（那是某个具体货币的痕迹）。

**这直接推翻了此前写死的"插件之间不互相依赖"**：商城/记账/刮刮乐都需要 `activeCurrency`。
处理方式定为软依赖——检测不到就引导，不崩、不阻塞、不做依赖解析。

## 为什么把"防作弊"从设计主线撤掉

曾经设计了"防止用户虚报工时刷分"。用户指出：这是**自激励**系统，作弊等于骗自己，动机天然很低，
真正的问题是"**开局配置成本太高**"。

于是目标从"堵漏洞"改成"零配置可用"：给一套自洽的默认值（时长档位、商品模板、货币参数），
并加一个更有效的功能——**把价格翻译成时间**（商品卡显示"≈ 攒 2 天"）。
用户自己看出失衡就会调，比任何校验规则都管用。

## 为什么数据层不换 drift

drift 能带来编译期列名检查、自动对象映射、`watch()` 响应式查询。
但：① 插件的动态建表吃掉了它最大的优势（只能退回 `customStatement` 裸 SQL）；
② 统计走 `SharedPreferences`，没有复杂查询压力；③ 本项目构建链已够麻烦（管道错误、git 走 API），
不宜再叠 `build_runner` codegen。

代价是"手写 SQL 的拼写风险"仍在，用**列名常量类**兜（182 处调用点、28 处手写 `fromMap`）。

**这是唯一的窗口期**：数据层重写时换库不额外花成本，之后再换就要返工 182 处调用点。
所以这个决定要在重写**之前**做，不能拖。已在重写前定：**保持 sqflite**。

## 为什么"日历条形态"是设置项，不是插件

用户问过"日历条固定一周 / 可横滑能不能做成插件选"。

**技术上能做，但做出来是假的。** 插件不能提供 Dart 代码，所以"插件选形态"的真实含义是：
主包把两种形态都实现好，插件只负责说一句"我选第二个"。这层开关约 20 行，
而它带来的成本是一整套插件安装流程——装、校验、入口、卸载，一步不少。

插槽（`SlotId`）的定位是"**内容由插件提供、主包不知道内容是什么**"。
日历条形态反过来：主包完全知道有哪几种，只是让用户挑一个。
**这是"呈现策略"，属于设置项；把设置项包装成插件，只会让用户多点两下。**

什么时候它才值得升成插槽？两个条件任一成立：
① 形态多到 5 种以上，主包全内置不划算；② 要允许外部提供新的形态（但插件无法提供 Dart 代码，
所以这一条在 WebView 模型下也不成立）。目前一条都不满足。

> 同类判断以后都适用：**先问"插件能不能提供主包没有的东西"，不能就放设置里。**

## 删除是"直接删"还是"进回收站"：做成开关，默认直接删

两种用户都存在：有人希望"手滑删了还能捞回来"，有人不希望手机里悄悄堆垃圾。
所以给开关，而不是替用户选。

- **默认关**：左滑即物理删除（`DELETE FROM tasks`），回收站里不会留下任何东西
- **开启后**：整行拷进 `recycled_tasks`，可按 `1 / 3 / 7 / 30` 天保留，期间可恢复
- **到期清理不做后台服务**：清理是**机会式**的，三个触发点 ——
  启动时、改保留时长之后、进回收站页时（都调 `purgeRecycleOlderThan`）。
  这是离线应用，用户不开 app 的那几天"过期数据还留着"没有实际影响，
  为此常驻一个调度器不划算
- **"倒计时"只是展示，不是计时器**。它按当前保留天数现算，
  所以改设置必须顺带清理一次，否则会出现"显示即将清理却一直挂着"——
  界面在骗人。**改短且确实会删东西时先弹确认框并写明条数**，取消则什么都不变
- **改长不会让已清掉的条目回来**（物理删除不可逆）
- **恢复会拿新 id**（原 id 已让给自增序列）
- **标签跟着回来**：删除时把 tag id 存进 `recycled_tasks.tag_ids`（快照），
  恢复时按它重建 `task_tags`。唯一会丢的情况是那个标签在这期间被删了 ——
  外键不允许指向不存在的标签，只能跳过它，而不是让整条恢复失败

### 这一轮引入了 v6 的第一条迁移（1 → 2）

`recycled_tasks` 加 `tag_ids` 需要改表，所以 `dbVersion` 从 1 升到 2，
`onUpgrade` 从"直接抛错"变成真的迁移链：

```dart
if (newVersion > version) throw ...;      // 版本超出本代码认知就失败
if (oldVersion < 2) ALTER TABLE ... ADD COLUMN tag_ids TEXT;
```

写法上刻意用「低于目标就补一步」而不是 `if (old == 1)`：
老设备可能停在任意版本，二分式写法迟早漏掉跨多版本的情况。

**这类迁移必须有一条"造一个真老库再打开"的测试**（`test/core/data/v6_migration_test.dart`），
否则升级用户的崩溃永远测不出来 —— 其余测试全跑在新库上。

为什么不默认开："缓冲"是有代价的（占存储、要清理、恢复后还缺标签）。
默认开等于让所有人替少数人的手滑买单。

## 标签管理是主包功能，不是插件

标签是任务的**基础维度**：任务卡片要显示它、筛选要按它、回收站恢复要带它。
插件只会在插槽里读它，不会替换它——按"插件能不能提供主包没有的东西"这条判据，
它属于主包。

页面只做标签本身的增删改（名称、颜色），不做"给任务打标签"——那是任务编辑的事，
目前只在新任务对话框里可选。

两个容易漏的点，已经写进测试：
- **改名后正在生效的筛选要跟着改**：筛选条件存的是标签名，不改就会指向一个
  不存在的名字，列表变空而用户以为任务丢了
- **删掉正在筛选的标签，筛选回退到「全部」**：否则列表永远是空的

删除标签只删掉关联（`task_tags` 靠外键 CASCADE），**不删任务**，确认框里写明
"有 N 个任务正在使用"。`tagUsage` 只统计 `tasks` 里的任务，回收站里的不算。

## 任务编辑用全屏页，"改"终于成为一等动作

在这之前任务只有"增"和"删"：标题、日期、优先级、时长、标签全部只能在新建那一刻
决定，之后再也改不了。标签管理做完后这个缺口更明显（打完标签改不了，只能删了重建）。

**为什么是全屏页而不是底部弹层**：字段会继续长（描述/日期/优先级/时长/标签，
将来还有循环、提醒、附件）。弹层里再叠键盘和 chip 会挤到没法用；
全屏页的另一个好处是将来插件可以往编辑页加插槽位。

**交互分工**：
- 左侧圆圈 = 勾选（保持原样）
- 点卡片正文 = 进编辑
- 左滑 = 删除
- 编辑页内也有删除入口 —— 不能假设用户知道"左滑才能删"

**删除仍在壳层做**：确认框、回收站开关、"以后不再提醒"这些规则只写一份，
编辑页通过 `onDelete` 回调请求删除，拿到 `true` 才关页面。

**顺手修的文案谎话**：删除确认框以前无论回收站开没开都写"将移入回收站"，
而默认是关的 —— 那等于告诉用户"还能从回收站捞回来"。现在按开关分叉：
开着说"移入回收站"，关着说"将被彻底删除，无法恢复"。

**未做**（记下来，别以为是漏了）：编辑页没有"改日期后提示已移到别的天"，
只在保存后统一提示"已保存"；循环任务、提醒、附件都没有。

## 创建和编辑用同一个页面（补一条重要修正）

上一轮做完全屏编辑页后暴露一个问题：**创建时只能填标题+标签，编辑时却能填六个字段**。
这等于所有任务都要操作两遍（先建、再进去补）。

现在加号直接进同一个全屏页：
- 新建模式：标题为空、自动聚焦、日期默认首页当前选中的那天、无删除入口、按钮叫「添加」
- 编辑模式：预填当前值、按钮叫「保存」、底部有「删除任务」

**一个页面两种模式，而不是两个页面**：两个页面的字段一定会分叉
（谁还记得住哪边多了哪个字段？），共用一套字段就没有"创建时填不了"的空间。

代价：快速记一件事比原来的弹窗多一次页面转场。如果以后这个成本变得明显，
可以再加"快捷添加"（只有标题的轻量入口），但**不能反过来把字段搬回弹窗**。

## 预览壳补上中文本地化

`MaterialApp` 原来没配 `localizationsDelegates`，导致 Material 自带的日期选择器、
文本选择菜单全是英文。v5 的 `main.dart` 一直有配，v6 预览壳是漏的。

配了 `GlobalMaterialLocalizations` + `supportedLocales: [zh_CN, en_US]` + `locale: zh_CN` 之后，
日期选择器直接是中文（"确定/取消"、"2026年10月"）。**这不需要插件，配置就能解决。**

"日期选择器可被插件替换"另说 —— 见下一条。

## 编辑页的可扩展性：先记下，不实现

用户希望编辑页将来"高度自定义"，日期选择器也希望可替换。现实约束：

- **插件无法提供 Dart UI 组件**（AOT 没有运行时加载）。所以"换一个更漂亮的日期选择器"
  在 Flutter 里只能是**主包内置多套 + 设置项切换**，或者**整页交给 WebView 插件**
- 区域级插槽（A 档）只能供数据，画还是主包画

可行的三条路（都还没做）：
1. **设置项**：内置 2~3 种日期选择（系统 / 主包自绘月历 / 周条），用户选 —— 便宜，但不是插件
2. **页面级接管**：编辑页里点日期 → 打开声明了 `picker:date` 能力的 WebView 插件 →
   插件用 bridge 回传选中的日期。要新增一条"插件反向取值"的 bridge 协议（目前只有宿主调插件）
3. **编辑页插槽化**：把编辑页拆成若干区域插槽（字段顺序、附加字段由插件供数据），
   风险和"父模块"一样 —— 每开放一个点，主包每次改动都要回头检查插件

第 2 条是唯一真正"插件替换"的形态，但它要新增一个**宿主等待插件返回**的协议，
属于新机制，得单独设计；第 1 条最便宜，先把体验做好。

## 编辑页自定义：字段归主包，插件只给整页（2026-10-26）

前面三轮把方案越推越复杂（字段 DSL → 插件字段存 EAV → 预留槽位列），
最后全部作废。结论：

- **字段永远在主包**。字段一旦要参与排序/筛选/统计，就得是真实列 + 索引；
  JSON 和 EAV 都做不到，插件也跑不进模型层。
- **插件只提供"一整个画好的页面"**（WebView）。用户不需要插件帮忙"渲染"，
  只需要它整块替换 —— 这也把插件的能力边界说清楚了：能加页，不能改字段。
- **null ≡ 字段默认值**，不设哨兵、不做三态。用户提的"清空和没填保持同一状态"
  顺手把筛选口径也统一了（所见即所筛）。
- **默认值绝不回写**。没动过的字段保存时仍写 null，否则改默认值对老数据失效。
- **加字段 = 一列 + 一条**。v5 那种"每个字段配个硬编码 boolean"不再重复。

编辑页形态做成"主体 + 容器"，默认底部弹层，设置里可切全屏。
上一版是全屏，理由写的是"字段会越加越多，弹层挤"，实际用下来弹层更像
移动端原生的新建动作，且不离场。

## 可换首页必须自带熔断（2026-10-26）

插件当首页有一个天生的问题：它把启动拖死时，用户没有界面可以操作。
所以三件套一起做，缺一不可：会话标记（上次有没有渲染成功）、2 秒首帧超时、
连续 2 次失败自动切回内置并落库。**外壳永远不交给插件** —— 底栏和侧边栏在
主包手里，插件崩了用户才有路可退。

## 默认值：新建落库、编辑不回填（2026-10-26 修正）

上一版写成"默认值只在读时生效、绝不回写"，验收时被打回：设了默认 60 分钟，
新建任务的卡片上仍然没有时长 —— 用户理解成"设置没生效"，程序却在坚持一个
它自己发明的设计。

改为按模式切分：**新建时没动过就写默认值**（用户设默认就是想要这个结果），
**编辑时没动过保持原值**（否则改默认值会顺手改写历史数据）。
一条规则管两件事是这次出错的根源。

## 编辑弹层的三个关闭开关全部关掉（2026-10-26 实测后）

`DraggableScrollableSheet` 的 `shouldCloseOnMinExtent` 默认是 `true`：拖到最小高度就
`pop` 掉整个路由。表现是"改到一半往下一拉，面板没了"，而且绕过 PopScope 的「放弃修改？」。
同一个问题还存在于点遮罩和模态层拖拽（两者都是 `Navigator.pop`）。

所以三个都关：`shouldCloseOnMinExtent: false`、`isDismissible: false`、`enableDrag: false`，
尺寸只留 62% / 100% 两档，关闭只剩左上角 X（有改动会先确认）。
取舍是牺牲"下拉关闭"的手感，换"改动不会无声消失"。

## 模式是"随手切"的，不是设置页里的单选项（2026-10-27）

原来切首页要：侧边栏 → 首页模式 → 点单选。三步，而且"设置"这个词让人以为
是改一次就不动的东西 —— 多模式就死在这一步。

改成顶栏标题右侧一个小箭头，点开底部弹层直接选。设置页保留，负责解释与
失败告警（那些不适合塞进一个快捷弹层）。两处共用 `buildModeOptions()`。

**插件模式下不画 `+` 按钮。** 主包不知道插件里"新建"是什么意思（写日记？
记一笔？），留一个 `+` 去建任务，用户会以为"新加的东西没存上"。隐藏而不是
灰掉：灰掉的按钮看着像没配置对，还会一直被点。

## V5 → V6 原地升级：能，缺的是迁移而不是更新器（2026-10-27）

评估结论记在 `docs/self-update-v5-to-v6.md`。要点：

- V5 已有完整自更新（清单 → 多源下载 → sha256 → FileProvider → 系统安装器），
  且 `REQUEST_INSTALL_PACKAGES`、FileProvider、release 签名都在
- 包名相同 → 覆盖安装；versionCode 必须是 `6.0.0+较大值`（现在是 `+0`）
- **真正的洞是数据**：v5 写 `v5_tasks.db`，v6 读 `v6_tasks.db`。不迁移 = 升级后空列表
- 结构差异很小：tasks / recycled_tasks / tags / task_tags 四张表基本 1:1，
  只丢 `reward_points` / `is_deducted`（v6 已移出到插件）
- settings **不迁移**：v5 是 camelCase、v6 是 `ui.*`，语义也不同，用 v6 默认值更干净
- **第二个洞**：v6 外壳里没有任何 updater，直接发出去就是"绝版包"

## V5 数据全部舍弃，不做迁移（2026-10-27）

原本打算写一个 `V5Migration`（四张表基本 1:1，只差 `estimated_minutes` 与 `tag_ids`）。
定案是不写。理由不是"迁移难"，是**迁移没意义**：

- V6 把积分、商城、刮刮乐、番茄钟全移出到插件，主库只留任务/标签/设置。
  就算把任务搬过去，用户升级后面对的还是个功能少一半的应用 ——
  "保住旧任务"只是把割裂感往后挪一步。
- 迁移是"只跑一次、出错就无法挽回"的代码。不需要就不写。

配套三条：
- **旧库不删。** 删它没收益，却会永久销毁用户数据；留着还顺带保住"重装 V5 能读回来"这条路
- **升级说明必须写明旧任务不会出现在 V6 里。** 用户点下更新那一刻是唯一能告知的时机
- **验收只剩一条**：装 V6 → 空列表 → 能新建任务

## V6 成为正式入口，旧入口降级为对照（2026-10-27）

- `lib/main.dart` → `V6PreviewApp(autoSeed: false, checkUpdate: true)`
- 旧 v5 入口另存 `lib/main_v5_legacy.dart`，只在本机对照用，不进发布包
- `pubspec` 版本 `5.5.26+0` → `6.0.0+6000`：**versionCode 原本是 0**，
  不涨就装不上（Android 只比整数），而且失败提示不会说明原因
- V6 外壳接上更新器（`AppUpdateProvider` + `.value` + `AppUpdatePromptHost`）。
  不接的话，新包发出去就是最后一版

`update.json` 暂时不动。顺序必须是"先传 APK，再改清单"，反过来会让所有
V5 用户收到更新提示、点下去是死链。

## 更新渠道一分为二：V5 冻结在 6.0.0，V6 自己一份清单（2026-10-27）

6.0.0 对 V5 只是一次**可选的引流**，不是强制的迁移。所以要把"一次邀请"
和"长期共用"分开：

- V5 → `update.json`，发完 6.0.0 后冻结：`latest.version` 不再涨、
  `minSupported` 保持 5.0.0（提了就等于强制更新，「跳过此版本」会失效）
- V6 → `update_v6.json` + `v6` 前缀的本地状态
- 清单地址在 V5 代码里写死，改不了 → **只能让 V6 换名字**，反过来不成立

本地状态必须隔离，最硬的理由是资源包构建号：V5 应用过 build 5，V6 读到会
以为自己也应用过，静默跳过 V6 的热更，且永远不会自愈。
"关闭提醒""跳过版本"一起隔离 —— 换了个应用形态，值得重新问用户一次。

`AppUpdateService` 的清单名与 Contents API 地址都改成按渠道生成，
避免 CDN 全挂时 V6 去读 V5 的清单，把 5.x 的更新当成自己的。

两条防呆断言（`test/core/updater/update_manifest_guard_test.dart`）：
`update.json` 的 `minSupported` 主版本 ≤ 5、`latest.version` ≤ 6.0.0。
这类改动在 review 里极不显眼，只能让测试挡。

## 插件升级走"覆盖安装"，卸载默认保留数据（2026-10-28）

**没有升级通道时，用户想升级只能"卸载再装"，而卸载会 DROP 插件表。**
等于用升级惩罚了用户 —— 攒了半年的记录被一次"我想用新版"清掉。
所以升级就是**对同一个 id 再走一遍 `install`**：目录按版本区分、
旧版本目录成功后删掉、`plg_<id>_*` 表不碰，数据自然都在。

三条配套决定：

- **升级不触发 `onInstalled`。** 那个回调的语义是"全新装上，先把初始状态
  报上去"（货币写 0 点亮徽章）。升级时再报一次 0，会把余额清空。
- **卸载分成"留数据"和"删数据"两条，默认留。** 卸载是"我不想用了"，
  不等于"把数据扔了"；而删是 `DROP TABLE`，没有回收站可退。破坏性的那个
  选项必须用户主动勾选，且提示条要说清到底删没删。
- **删数据要清干净三类键**：`plg.<id>.*`（插件 KV）、`currency.balance.<id>`
  （主包替它存的镜像）、`sys.home_failures.<id>`（首页熔断计数）。
  只删表不清键的话，重装回来顶栏会显示一个**陈旧余额** ——
  比"什么都没有"更让人以为见鬼了。

两个容易错的地方：

- 前缀匹配**不能用 `LIKE 'plg.<id>.%'` 直接当判据**：`_` 在 LIKE 里是单字符
  通配符，而插件 id 本身就带下划线，`plg.a_b.` 会误伤 `plg.axb.`。
  先用 LIKE 缩小候选，再用 `startsWith` 判定。
- **卸载必须通知应用层**（`onUninstalled` → `HomeModeStore` /
  `CurrencyStore`）。不通知的话 `ui.home_mode` 与 `ui.active_currency`
  会一直指着一个已经删掉的插件：表现是「首页模式」页打开后没有任何一项
  被选中，货币则靠"再查一次已装列表"临时兜住。

## 契约版本给机器看，不给用户看（2026-10-28）

插件页原来挂着一行「契约 1 · v1.0.0」，用户问这行依据是什么。查下来：
**没有哪份需求要求回显 `contract`**，它是我照着市场页副标题
（`v1.1.0 · 契约 1`，`plugin_market_page.dart`）的习惯抄进插件页的，
顺序还反了。

`contract` 到底是什么：**插件与宿主之间的接口兼容版本**，与 App 版本、
插件版本都无关（`plugin_manifest.dart`：宿主只接受 `min..current` 区间的插件；
App 从 6.0 升到 6.3，只要扩展点接口没动，已装插件一个都不用重发）。

它对谁有意义、什么时候有意义：

| 场景 | 契约版本的作用 |
|---|---|
| 插件作者写包 | 决定声明 `contract: N`，写错了宿主直接拒装 |
| 用户装不上时排查 | 「插件要求 2、宿主只支持 1」——这时候才需要看见它 |
| 用户日常用插件 | **零可操作含义**：改不了、升不了、也不是他能理解的概念 |

所以定下：

- **插件页只显示版本号**（`v1.1.0`），契约不回显。页面上出现一个用户无法
  操作的数字，就只是噪音。
- **市场页保留「契约 N」**：那里本来就是"装 / 不装 / 能不能升"的语境，
  而且是唯一能直接对上"装不上"原因的地方。
- `system.info` 仍回 `contract` —— 回不回声是页面的事，桥不该替页面决定；
  以后要做"插件自检页"还得用。

顺带修掉的另一个问题：版本号以前写死在页面里，升级后还是旧号。现在一律
从 `system.info` 拿（`asset_index_test` 有守卫，倒退会红）。
