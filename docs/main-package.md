# 主包清单 v2（货币改为完全插件化）

> 2026-10-22 ｜ 基线 v5.5.26 ｜ 依据：仓库实际代码与 schema，不是旧文档
> **v2 变更**：货币（能量/积分）从"主包服务"改为"框架在主包、实现全在插件"。
> 用户明确：无真实用户数据，**v5 → v6 不必写迁移**，数据库格式可全改。
> 注意区分：v6 自己的迁移链从 `dbVersion = 2` 起已经开始积累
> （`recycled_tasks.tag_ids`），见 `docs/decisions.md`。

---

## 0. 判断原则（修订）

1. **被多方依赖的 → 主包只提供"框架/能力"，不提供"具体实现"**
2. **需要系统能力的（通知/后台/小组件）→ 主包提供能力**
3. **其余一切 → 插件**

第 1 条是关键修订：v1 把货币账本放进主包，v2 收回框架、把账本交给插件。

## 4. 货币：框架在主包，实现全是插件

### 4.1 主包只提供框架

- `CurrencyRegistry`：登记已安装的货币
- `activeCurrency`：当前生效的那一个（**同一时刻只有一个**）
- 统一接口：`balance()` / `earn(n, reason)` / `spend(n, reason)` / `records(limit)`
- **主包不知道有"能量"或"积分"这种东西**，只知道"有个货币实现被注册了、现在是它"

### 4.2 两套实现，两个插件

| 插件 | 产出规则 | 存储 |
|---|---|---|
| **能量**（`energy`） | 随时间自然恢复 + 每日签到 | `plg_energy_*` |
| **积分**（`points`） | 任务完成按预计时长发放 | `plg_points_*` |

**任务表不再存任何货币字段**（`reward_points` / `is_deducted` 移除）。
货币插件用自己的表记录"哪个任务发了多少、发过没有"。

### 4.3 冲突处理

用户可同时装两套。**同一时刻只有一个 `activeCurrency` 生效**，其余处于"装了但不活跃"状态（数据保留、不产出）。

- 优先级只用来**推荐默认值**（例如积分高于能量）
- **真正切换由用户显式执行**（设置里选"当前使用：能量 / 积分"）
- 理由：自动按优先级切换会让用户困惑（"我装了两套，为什么只有一套在动"）

### 4.4 「开关」还需要吗

v1 设了"能量服务总开关"。货币完全插件化之后，**开关 = 装不装插件**，
所以建议**取消独立开关**，少一个概念，也少一处状态要对齐。

> 若你仍想要"装了但临时停用"的能力，那才需要开关（默认关）。

### 4.5 任务时长档位归谁

- `tasks.estimated_minutes`（可空）是**中性的任务属性**，归主包
- 主包只在"存在 activeCurrency"时**显示**这个选择器；没有就不显示
- 主包知道"有没有货币"，但不知道是哪种货币 —— 这个耦合程度是刻意的

## 5. 数据切分（v2 重排）

### 5.1 主包表（5 张业务表 + 1 张基础设施表）

`tasks`（去掉 `reward_points` / `is_deducted`，新增 `estimated_minutes`）、
`recycled_tasks`（同构调整）、`tags`、`task_tags`、`settings`，以及 `plg_migrations`。

**番茄钟的两张表已移出主包**（2026-10-22 决定）：
- 会话记录与番茄钟设置 → 插件的 `plg_pomodoro_records` / `plg_pomodoro_settings`
- 主包计时引擎只保留**运行时状态**（"正在计时"的进度），存放在 `settings` 里——
  那是引擎自己的状态，不是业务数据；引擎结束一次会话时发 `pomodoro.sessionFinished`，
  由插件决定是否落库。**没装插件就不落库**，符合"关闭即无痕"。

### 5.2 插件表（随插件走，物理同库）

| 插件 | 表 |
|---|---|
| 能量 | `plg_energy_balance`、`plg_energy_records`、`plg_energy_checkin` |
| 积分 | `plg_points_balance`、`plg_points_records`、`plg_points_task_rewards` |
| 商城 | `plg_shop_items`、`plg_shop_purchases` |
| 记账 | `plg_ledger_entries` |
| 刮刮乐 | `plg_scratch_pool`、`plg_scratch_draws`、`plg_scratch_tickets` |
| 番茄钟 | `plg_pomodoro_records`、`plg_pomodoro_settings` |

规则：前缀 `plg_<插件id>_`，各自在 `plg_migrations` 记版本，主包迁移完全不知道它们存在。

### 5.3 既然没有真实数据，可以顺手清掉的历史包袱

- `database_migration_mixin` / `_core_tables_` / `_feature_tables_` 三张迁移 mixin 可整体删除
- `AppConfig.dbVersion = 3` 的版本链可归零重来
- 15 个 DB mixin 可以按新边界重整（不必保留"按模块拆"的旧形状）

**建议数据层仍用 sqflite**：插件的动态建表在裸 SQL 下最直接，不用引入 codegen。
如果你有换 drift 的想法，**现在是唯一的窗口期**，之后就没这个机会了。

## 7. 插件依赖：软依赖出现了（对 v1 的修正）

v1 写着"刻意设计成没有任何插件依赖另一个插件"。**货币插件化之后这条不再成立**：

- 商城 → 需要 `activeCurrency` 才能定价与扣费
- 记账 → 同上
- 刮刮乐 → 同上

处理方式定为**软依赖**：
- 启动时检测 `activeCurrency`，没有就显示"请先安装一个货币插件"的引导页
- **不崩溃、不阻塞主包**，也不做硬性依赖解析
- 契约里 `requires` 字段只用于提示，不用于强制

---

## 8. 准入规则（不变）

> **进能力层必须满足其一：① 被两个以上插件依赖；② 需要系统能力；③ 是数据一致性的唯一入口。**

货币框架满足①，所以它在能力层；但它的**实现**不满足任何一条，所以在插件层。
这条界线以后每次都要问一遍。
