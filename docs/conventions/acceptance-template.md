# 验收清单模板

> 最后更新：2026-11-01

## 文件骨架

```markdown
# 验收 · <主题>（<日期>）

> 对应提交：`<sha>` ｜ 环境：`flutter run -t lib/main_v6_preview.dart`
> 结论：未验收 / 通过 / 部分不过（不过的编号：　）

## 准备
1. …
2. …

## 零、已自测（机器判定，不需要你动手）

只列证据，供抽查。**这一节不该出现“你打开看看”这类要求。**

| # | 断言 | 证据 |
|---|---|---|
| A1 | 关掉字段后编辑页不再画它 | `task_editor_fields_test.dart` › 关掉「预计时长」后… ✔ |
| A2 | 默认值新建时落库、编辑时不回填 | 同上 › 默认值在新建时落库 / 默认值不回填已有任务 ✔ |

## 一、需要你判断（≤10 条）

凡是手感、观感、产品取舍。代码可判定的**不许**放进来。

| # | 路径 | 操作 | 预期 | 不过时先看 |
|---|---|---|---|---|

## 二、已知未做 / 已知限制

- 真机手感未验证：B1、B2
- bridge 仍只读，插件改不了任务数据
```

> 分组只留两层：**零（机器判定）** 和 **一（人判定）**。
> A/B/C/D 四组看着整齐，实际会把“我自己跑一下就知道”的条目混进去，
> 用户只能逐条替你复现，纯浪费时间。

## 好的预期 vs 坏的预期

| 坏 | 为什么坏 | 好 |
|---|---|---|
| “编辑页显示正常” | 「正常」是谁的判断？ | “编辑页出现 标题/日期/优先级/标签/描述/预计时长 六行，顺序与此一致” |
| “弹层手感好” | 无法判定通过与否 | “从底部上拖 300px 后松手，弹层停在满屏；再下拉 200px，回落到约 62%” |
| “数据不丢” | 看不出丢没丢 | “关掉「描述」后重开该任务，描述内容仍在（点底部「已隐藏 描述（内容还在）」可展开看到原文）” |
| “性能可以” | 没有基线 | “冷启动到出现底栏 ≤ 1.5s（同机型对比不慢于上一版）” |
| “插件能装” | 装完能不能用没写 | “市场点安装 → 出现进度 → 完成后侧边栏多一项「周计划」；断网重开 App 仍能打开该页” |

## 三个写法要求

1. **一步一编号。** “改了默认值再新建任务看是不是预填” = 两条（改 / 看）。
2. **数量要写死。** “出现若干标签” → “出现 2 个标签：工作、学习”。
3. **失败要能定位。** 每条给一个“先看哪个文件”，省掉来回问。

## 手感/平台类条目

测试只能锁“有没有这个特征”，锁不住“好不好”“点不点得着”。凡是这种条目：

- 单独标注「需真机」，不要混进机器判定。
- 交付说明里必须写“未在真机跑过”，不许用“测试全过”顶替。
- 允许主观结论，但通过标准要写成可观察的动作（拖多远、松手停在哪、点哪个坐标）。
- 弹层、键盘、Insets、SnackBar 持久化、通知权限，都属于这一类。

## 回归组（D）

改 A 功能弄坏 B 功能是常见事故。每次交付至少保留 3 条上一轮验过的关键路径，
例如：左滑删除、切日期不重建、回收站恢复带标签、插件升级后首页刷新。

## 自动化覆盖一节

在清单末尾写：

```markdown
## 自动化覆盖

`flutter test` 562 通过（上一轮 549，+13）。
新增锁点：
- `test/app/xxx_test.dart` —— …
- `test/core/xxx_test.dart` —— …
```

数字必须与真实运行一致；新增/删除测试要说明理由。
