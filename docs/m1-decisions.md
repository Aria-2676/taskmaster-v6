# M1 产品裁决：对照搬行为 decided「照搬 / 修 / 延后」的逐条裁定

> 依据：`docs/migration/spec-points-shop.md`（积分/商城/标签/回收站）与 `docs/migration/spec-tasks.md`（任务）。
> 原则：**功能尽量保留**（作者要求），但「保留一个能刷分的漏洞」不叫保留功能——那是要修的 bug。
> 每条都注明「为什么这么定」，避免后来人以为是随手写的。

## 总原则

| 类别 | 处理方式 |
|---|---|
| 可观察的产品行为（数值、文案、流转） | **照搬**，不擅自改进 |
| 明显 bug（数据不一致、崩溃、可以刷分） | **修**，并在代码里注明「这是修，与 Flutter 版不同」 |
| 需要改 schema 才能修的 | **延后到 v6.x**，M1 照搬并写注释说明已知缺陷 |
| 纯内部实现细节 | 照搬等价语义即可 |

---

## 逐条裁决

### H1 · 任务恢复后 id 变化导致可重复刷分 → **修**

- **严重性**：用户可主动利用，无限刷分。`points_records.related_id` 和 `task_tags.task_id` 都指向旧 id，
  恢复后 `getLatestPointsRecord(新id)` 查不到 → 任务被当成「从未结算」→ 再加一次分。
- **裁定**：采用**方案 B**——恢复时把原 `id` 一并写回（`INSERT INTO tasks (id, ...) VALUES (原id, ...)`），
  并同步修正 `points_records.related_id` 与 `task_tags.task_id`。
- **为什么该修**：这不是「行为差异」，这是**数据完整性漏洞**，且修复不改变任何正常路径的用户可见行为。
- **实现注意**：原 id 在 `tasks` 中必然不存在（`AUTOINCREMENT` 保证不复用），所以带 id 插入不会主键冲突。
  若插入时真的撞了（理论上不该），必须回滚事务并提示，**绝不能静默换 id**。

### H2 · 恢复任务要不要恢复标签 → **修（顺带）**

- `recycled_tasks` 没有标签快照列，所以恢复后标签关联丢失。但**孤儿行还在** `task_tags` 里（H4 裁定不清理），
  所以只要 id 保持不变，**标签会自己接回去**，无需任何 schema 变更。
- 裁定：H1 的修复**自动解决**了 H2。这是把两件事一起修的收益。
- 若 H4 改成「删任务清 `task_tags`」，此修复就会失效——所以 H4 必须裁定为「不清理」。

### H3 · 恢复循环任务触发大规模回补 → **延后到 v6.x，M1 照搬并注释**

- 删掉 3 个月前的每日任务再恢复 → 按「无下界」窗口生成 90+ 实例，把任务列表淹掉。
- **为什么 M1 不修**：修它需要定义「夹到今天起」这类新语义，属于**产品行为变更**，
  不是 bug 修复。擅自改会让 v6 与 v5 的行为出现用户可感知的差异。
- M1 必须：在 `restoreTask` 的代码注释里写明此缺陷与影响，并在 UI 上给一个提示
  （恢复循环任务时提示「将按现有规则补齐循环实例」）。

### H4 · 删任务是否清理 `task_tags` → **不清理（照搬）**

- 照搬才能让 H2 的标签恢复生效。代价是 `task_tags` 会累积孤儿行。
- **但不修就等于留着脏数据**，所以配套决定：**启动时做一次孤儿清理**，
  只删 `task_tags` 中 `task_id` 在 `tasks` 和 `recycled_tasks` 里都找不到的行。
  这样既保住 H2 的恢复能力（回收站里的 id 不算孤儿），又不让脏数据无限增长。
- ⚠️ 这会让 `verifyGolden` 的 `task_tags` 行数检查漂移 → **验收 SQL 要相应调整为
  「孤儿数 = 0」而不是「行数 = 固定值」**。这一条要同步改 `schema-v3.md §7`。

### H5 · `markTaskDeducted` 无条件执行 → **照搬 + 注释**

- `reward_points == 1` 的任务 `floor(1/2) == 0` 不扣分，但 `is_deducted` 仍被置 1。
- 影响：无（本来就不会扣第二次，因为扣分条件里 `is_deducted = 0` 是门槛，置 1 反而是**正确**的幂等保护）。
- 裁定：照搬，注释说明「这看起来像 bug 但其实是幂等保护，不要『修』」。

### H6 · 仓库页按快照 name 分组 → **照搬**

- 商品改名会分裂成两组、同名会合并成两组。确实是怪现象，但属于既定行为。
- 裁定：照搬。若用户反馈再改。

### H7 · `shop_purchase.related_id` → `shop_items.id` → **照搬**

- 纯事实确认。对账 SQL 必须按这个写，否则全错。

### H8 · 编辑标签名撞 UNIQUE 抛未捕获异常 → **修**

- 用户遇到就是崩溃。`RepoError` 已能把 SQLite 原文翻成「已存在同名记录」，加上 try/catch 即可。
- 裁定：修。属**不改变正常路径行为**的纯健壮性修复。

### H9 · `custom_prize_pool` 两份 DDL → **延后**

- `database_schema_mixin.dart:100`（严格版）与 `database_scratch_mixin.dart:10`（旧版）冲突，
  无法确认 `createScratchTables` 是否仍被调用。`rn/src/db/schema.ts` 采用了严格版。
- 裁定：M1 不涉及刮刮乐（M3 才做），保持现状并在 `schema-v3.md` 标注「存在两份 DDL，严格版为准，旧版疑为死代码」。
  等 M3 做刮刮乐时再彻底确认。

### H10 · 埋点 `StatisticService` 是否迁移 → **不迁移**

- 本地存储、无功能依赖。M1 不做统计模块（M1 只做任务/标签/积分/商城/回收站）。
- 裁定：M1 不迁移。若 v6.x 要做游戏/统计，届时再一并实现（含 2000 条上限）。

### H11 · 回收站文案「保留一段时间」不准确 → **修（文案）**

- 实际只保留最近 10 条。文案误导用户。
- 裁定：文案改为「仅保留最近 10 条」。行为不变。

### H12 · 永久删除无二次确认 → **修（交互）**

- 误触即永久丢失，不可逆。
- 裁定：加二次确认对话框。行为不变（只是多一步）。

### H13 · RN 全新安装不插 3 条示例任务 → **修（补齐）**

- 与 Flutter 版首装体验不一致。纯新增，不影响迁移路径（迁移路径下库里已有真实数据，`INSERT OR IGNORE` 不会重复插）。
- 裁定：补上，插进 `rn/src/db/schema.ts` 的 `SEED_SQL`，照抄 Flutter 版那 3 条的真实文案。

# 追加裁决 · QA 独立核查后（第二轮）

> 来源：`docs/migration/spec-review.md`（QA 独立核查 + 真实 MySQL 5.7 容器跑 Flutter 侧测试 65/65 全绿）。
> 这一轮推翻了两条「死代码」判断，并发现两处**会让 H1 修复失效**的漏洞。

## P0-1 · `getRecycledTasks` 有**两个都活着**的实现 ⚠️修正此前的死代码判断

此前两份规格都断言「`database_task_mixin.dart` 的方法都是死代码，只有 `TaskRepository` 生效」。**这个判断是错的**：

```
lib/core/services/database/database_task_mixin.dart:257  getRecycledTasks()  → 返回 5 个字段
  └─ 被 lib/modules/profile/pages/data_export_page.dart:300 调用   ← 活的（数据导出页）
lib/modules/tasks/repositories/task_repository.dart:396   getRecycledTasks()  → 返回 10 个字段
  └─ 被 lib/providers/mixins/task_provider_core_mixin.dart:100 调用 ← 活的（回收站页）
```

**裁定**
- 修正 `spec-tasks.md §3.1` 与 `spec-points-shop.md` 的死代码清单：**不是死代码，是同名两实现**。
- RN 侧 `recycleRepo.listRecycled()` **只实现一个**，返回完整 10 列（含 `task_id` / `deleted_at` / `priority` / `is_word` 等）。
- **M1 不做数据导出功能**，所以那个 5 列版本没有对应实现；但要在规格里留档：
  若将来做数据导出，**不能直接复用 10 列版本**——旧导出格式只含 5 列，多导出列会破坏既有导出文件格式。

## P0-2 ·「仅恢复当天」绕过 H1 修复 ⚠️**必须改**

回收站对话框对循环任务给两个选项（`recycle_bin_page.dart:226-243`）：

| 选项 | 实现 | 是否走 H1 修复 |
|---|---|---|
| 「恢复循环」 | `taskProvider.restoreTaskFromRecycle(id)` | ✅ 走 |
| 「仅恢复当天」 | `copyWith(recurrence:'none')` → `deleteFromRecycle()` → `addTask()` | ❌ **不走** |

第二条路径里 `addTask` 最终走 `insertTask`，**不带 id** → 同样拿到新 id → **H1 的修复对它完全无效**。
而这恰恰是循环任务最容易命中的路径。

**裁定：M1 把两条路径合并为同一个仓储方法**，参数化一个「是否保留循环链」的布尔：
- 两条路径**都**保留原 id；
- 两条路径**都**在同事务内修正三处引用；
- 顺带修掉「非原子 delete + add」（现状中间态会短暂让任务消失）。

## P1-1 · H1 的引用修正漏了两处 → 补齐

原裁决只提了「`points_records`（限 `task_complete` / `task_uncomplete`）」与 `task_tags`。实际**共 4 处**引用：

| 表.列 | 指向 | 用途 |
|---|---|---|
| `points_records.related_id`（type = `task_complete` / `task_uncomplete`） | `tasks.id` | 加分与冲销幂等 |
| `points_records.related_id`（type = **`overdue_deduct`**） | `tasks.id` | **逾期扣分幂等 —— 补上后，一条任务被删→恢复→再逾期，不会二次扣钱** |
| `pomodoro_records.related_task_id` | `tasks.id` | 番茄钟关联的任务标题快照 |
| `task_tags.task_id` | `tasks.id` | 标签关联 |

若因主键冲突回退到新 id，**这 4 处必须同事务一起改**。
但注意：**主键冲突在实践中不会发生**（`tasks.id` 是 AUTOINCREMENT，删掉的 id 不会被复用），
所以正常路径永远是「保留原 id + 不改任何引用」。回退分支只是防御性的。

## P1-2 · 小组件桥接 ⚠️**本条曾写错，已按代码事实重写**

**原表述有三条事实错误**（我照抄了核查报告而没有自己验证，教训见文末）：
`lifecycleBridge` 符号在仓库里**不存在**；`task_points_mixin.dart` / `task_tag_mixin.dart` **这两个文件不存在**；
`pubspec.yaml:41` **有** `home_widget: ^0.6.0`。所以「缺依赖导致调用 no-op」这个理由是错的。

**真实机制**（`lib/providers/mixins/task_widget_mixin.dart`）：
```
_debouncedUpdateWidget()   // 300ms Timer 防抖（:9）
  → _performWidgetUpdate()  // :29
     → HomeWidget.saveWidgetData() ×4（:52-57）+ HomeWidget.updateWidget()（:63）
```
共 **5 处**调用：`task_provider.dart:80`、`task_crud_mixin.dart:15/70/81`、`task_batch_mixin.dart:115`。

**裁定**：小组件代码在 Flutter 侧**是在真实工作的**（不是死代码）。M1 是**主动裁掉这项功能**，
因此 `TaskWidgetMixin` 整个 mixin 与 5 个调用点在 RN 侧**不实现**。

⚠️ **为什么这条区别重要**：若按旧表述（"既有 no-op，不用管"）理解，实现者会留下空壳或未解释的缺口；
正确理解是「有意裁剪，M2 接小组件时补回」。届时直接复用 Spike 已真机验证过的 `DevControl.updateWidgets()`
与 `TaskWidgetProvider.refreshAll()`，不必再研究 `home_widget` 的数据格式。

# 追加裁决 · 第三轮（仓储层实现后）

## T1 · 逾期扣分的「双幂等」—— ⚠️**本条前提已被推翻，改写为实现红线**

> **原裁决的前提是错的**。原文写「编辑表单不传 `isDeducted` → 构造默认值 `false` → 第一道门重新打开」，
> 实际 `task_form_submit_mixin.dart:28` **显式传了** `isDeducted: widget.task?.isDeducted ?? false`
> → **编辑不会重置 `is_deducted`**。我引用 `task_model.dart:32`（构造器默认参数）指错了位置，
> 那个默认值只对**新建** Task 生效。原文整条推论不成立。

**核实后的真实机制**：逾期扣分有两道门，**是「与」不是「或」**——
1. `getOverdueTasks`（`task_repository.dart:252`）的 `WHERE is_deducted = 0`；
2. `_shouldHandlePoints(task, 'overdue_deduct')` 再按 `points_records.related_id + type` 查一次。

研究员扫了全仓 12 处 `isDeducted` 写入点，逐一核实：

| 路径 | `is_deducted` 行为 |
|---|---|
| 编辑任务（`task_form_submit_mixin.dart:28`） | 显式继承，**不重置** ✅ |
| 恢复任务（`task_repository.dart:361`） | 从回收站行还原，**不重置** ✅ |
| 循环实例生成 | `copyWith(isDeducted: false)`，但 `recurrence != 'none'` 被逾期 SQL 排除，进不了扣分循环 ✅ |

**⇒ 第一道门在现有代码里始终关着，「重复扣款」在 Flutter 现状下不成立。**

**改写为实现红线（这是本条唯一的实际价值）**

> 🔴 **RN 实现 H1（恢复时写回原 id）时，绝不能顺手把 `is_deducted` 重置为 0。**
>
> 那一刻起：id 变更已让第二道门失效（`points_records` 的 `overdue_deduct` 流水按新 id 查不到）；
> 若 `is_deducted` 又被置 0，第一道门同时失效 ⇒ **真扣用户积分、余额无下限保护**
> （`deductPointsWithRecord` 不传 `requireAtLeast`，`UPDATE` 只有 `WHERE id = 1`）。
>
> 这是**资金损失级红线的唯一触发路径**，而它只可能由 RN 实现引入——
> Flutter 现状没有这条路径，所以它不是「要修的缺陷」，是「实现时不能碰的约束」。

**顺带记录一处不对称**（既有行为，1:1 复刻即保留）：
编辑任务时 `isDeducted` 被显式继承，但 `createdAt` **没传** → 构造器默认 `DateTime.now()` → **被重置**。
同一个构造调用里，一个刻意保留、一个意外重置。这是 `spec-tasks.md §6.2 b` 的成因，
影响「按创建时间」排序与统计，M1 照搬不改。

### T1 附：`is_deducted` 全仓写入点穷举（7 处，逐一核实）

为回答「是否存在未覆盖的路径会把它写回 0」，我对全仓做了穷举，结论是**没有可达的归零路径**：

| # | 位置 | 行为 |
|---|---|---|
| 1 | `task_form_submit_mixin.dart:28` 编辑表单 | `widget.task?.isDeducted ?? false` → **继承原值** ✅ |
| 2 | `task_repository.dart:361` 恢复任务 | 从 `recycled_tasks` 行读回 → **还原** ✅ |
| 3 | `database_task_mixin.dart:287` 回收站写入 | 读取时原样带过去 ✅ |
| 4 | `task_model.dart:103` `Task.fromMap` | 读库映射 ✅ |
| 5 | `task_model.dart:192` `RecycledTask.fromMap` | 读库映射 ✅ |
| 6 | `task_model.dart:63` `copyWith` | `?? this.isDeducted` → **保留** ✅ |
| 7 | `task_scheduler_service.dart:97` 循环实例生成 | **`false`** ⚠️ |

**唯一置 0 的是第 7 处（循环实例）**，但它不可达扣分循环：
`getOverdueTasks` 的 `WHERE` 含 `recurrence = 'none'`，而循环实例 `recurrence != 'none'` → 被直接排除。

**⇒ 现���代码不存在把 `is_deducted` 归零的可达路径。** 红线的触发条件因此收紧为：
必须由 RN 代码主动引入（恢复时置 0、或新增批量操作时置 0）。
这条穷举也说明：**将来若在 RN 侧新增任何「批量重置任务」的入口，必须显式声明是否影响 `is_deducted`。**

## T2 · `schema-v3.md` §5.4 与 §7 的矛盾 → **两者都保留，只补时序说明**

§5.4 说「`task_tags` 很可能有孤儿行，迁移时不要假设外键已清理」；
§7 验收第 3 条要求「孤儿数应为 0」。看似矛盾，**实为两条不同用途的断言**：

- **§5.4 是防御性提醒**（「可能」有），用于告诉实现者不要写 `DELETE ... CASCADE` 就完事；
- **§7 是迁移验收硬门**（必须为 0），用于证明迁移过程**没有制造**新孤儿。

真实库实测孤儿数为 0（见 `spec-review.md`），所以 §7 的硬门是守得住的，也应该守住——
它正是「迁移没弄脏数据」的证明。

**裁定**
- **§7 判定标准不改**，孤儿数仍要求为 0。理由：迁移是一个应当保持数据原样、不引入任何变更的操作；
  放宽成「前后一致」等于允许迁移过程携带脏数据出库。
- **§7 加一句时序说明**：本节验收在**迁移完成时立即执行**；
  应用运行后的孤儿清理（`purgeOrphanTaskTags()`）**不参与本验收**，它发生在验收之后，不影响结论。
- 补充：`purgeOrphanTaskTags()` **不在启动时自动执行**（自动执行会让「迁移后立即验收」的结果不可预测）。
  改为两个触发点：① 用户在回收站「清空」时；② M2 提供的「清理无效标签关联」手动入口。
  启动时只做**读取**孤儿数用于展示，不做写入。

## T3 · 余额校验必须用 `db.transaction()`，不能用 `writeBatch()`

工程师在实现中发现：`executeBatch` 返回的是**总** `rowsAffected`，多语句场景下**无法判定是哪一条失败**。
而商城兑换/刮刮乐出票依赖「`WHERE points >= ?` 的 `affectedRows > 0`」判断成败。

**裁定：分层，并在 `repo/base.ts` 注明**
- `writeBatch()` **保留**，但**仅用于「全部语句都必须成功、且不需要逐条判定」**的场景
  （如裁剪回收站的多条 DELETE、批量播种）。调用方必须在注释里说明为何不需要逐条判定。
- 需要**判定成败**的场景（任何涉及余额校验的），改用 `db.transaction(async (tx) => { await tx.execute(...) })`，
  逐条拿 `rowsAffected`。
- 这是 `repo/base.ts` 的设计缺陷，已记录；实现层按上述分层执行。

## T4 · 逾期判定口径 —— **以代码为准，`core/points.ts` 要改**

`core/points.ts` 的 `isOverdue(cplTime, now)` 用 `cplTime < now`，
而代码真实行为是 **`cpl_time < 当天 00:00`**（今天到期不扣分）。

**裁定**：以代码为准。`isOverdue` 改为与 `localTodayRange().start` 比较，并在注释写明
「变量名在 Dart 侧叫 `endOfDay` 但实际是当天零点，是历史遗留的误导」。

## T5 · 「type 排序权重」不存在 —— 撤销该要求

我在给工程师的任务书里要求单测「排序权重」，**这是我凭空写的**：
`spec-points-shop.md A.8` 只规定了 `ORDER BY created_at DESC LIMIT 50`，没有任何权重概念。
**撤销该项要求**，不实现、不单测。

# 追加裁决 · 第五轮（孤儿清理的触发时机）

## V1 · `purgeOrphanTaskTags()` 的触发时机改为「永久删除的那一刻」，不是启动时、也不是手动

研究员指出：T2 让 purge 不在启动时跑之后，孤儿行仍会**持续累积**——
回收站硬上限 10 条，每删第 11 个就会把最旧条目**物理删除**，那些条目对应的 `task_tags` 行
随即在 `tasks` 与 `recycled_tasks` 里都查不到，变成孤儿。「清空回收站」更极端：一次让**全部**历史关联变孤儿。

**先纠正一个前提**：这**不是标签关联的「损失」**。
条目被裁剪 = 那个任务已经被**永久删除**，它的标签关联本就无处可挂。
留着这些行是纯粹的垃圾数据，不是可用信息。所以「清空前提示用户会失去标签关联」是**错的方向**——
用户并没有失去任何能用的东西，因为任务本身已经没了。

**裁定：把清理挂到「任务被永久移出回收站」的那一刻，与该删除同事务完成**
- 回收站裁剪（移入第 11 个导致最旧条目被物理删除）→ **同事务**删掉被裁剪条目的 `task_tags` 行；
- 清空回收站 → 同事务删掉这批 `task_tags` 行；
- 这样**孤儿数在任何时刻都是 0**，不需要启动时清理、也不需要手动入口、不需要后台任务。
- `purgeOrphanTaskTags()` 保留为**兜底**（用于历史遗留脏数据），但**不自动调用**，
  仅在「M2 设置页的手动清理入口」按需触发。

**收益**：§7 的「孤儿数为 0」在**迁移时点与运行期同时成立**，两套口径不再需要区分时序；
也不会出现「数据在用户看不见的地方悄悄被清掉」的情况——每一次删除都有明确的用户动作。

### V1 补充 · 还有两条永久删除路径会产生孤儿（V1 初版漏了）

研究员追问「是否还有未覆盖的删除路径」——我核实了全部删除入口，**V1 初版确实漏了两条**：

| 路径 | 位置 | 行为 | V1 初版 |
|---|---|---|---|
| 回收站内**单条永久删除** | `task_repository.dart:380 deleteFromRecycle` | 只 `DELETE FROM recycled_tasks WHERE id = ?`，任务**不恢复** → 该 `task_id` 的 `task_tags` 立刻成孤儿 | ❌ 漏了 |
| **批量删除循环任务** | `task_repository.dart:148 deleteTask(deleteAll: true)` | **物理删除**该 loop 中所有符合条件的实例，**不进回收站** → 这批 `task_id` 的 `task_tags` 全部成孤儿 | ❌ 漏了 |
| 回收站裁剪 | `_cleanupRecycledTasksTxn` | 移入第 11 个时物理删除最旧条目 | ✅ 已覆盖 |
| 清空回收站 | `clearRecycleBin` | `DELETE FROM recycled_tasks` | ✅ 已覆盖 |
| 单次删除（非循环） | `deleteTask` else 分支 | 进回收站，不产生孤儿 | — |

研究员的判断正确：**漏掉批量删除这一条，V1「孤儿数恒为 0」的收益就不成立。**

**补充裁定**
- `deleteFromRecycle(id)` → **同事务**清掉该 `task_id` 的 `task_tags` 行。
- `deleteTask(id, deleteAll: true)` → **同事务**清掉这批被物理删除实例的 `task_tags` 行。
  ⚠️ 附带一个原子性问题：Flutter 的批量删除是**循环 `await db.delete(...)`、不在事务里**
  （`task_repository.dart:158-162`），中途失败会留下「删了一半」的循环链。
  **M1 修**：把批量删除包进事务，与 `task_tags` 清理原子完成。
  理由：这是**原子性修复**而非产品行为变更；且既然要在同一处加清理，不包事务就无法保证一致性。

## V3 · 措辞修正：孤儿是「生命周期缩短」而非「不产生」

C.3 / F14 / X3 / H4 写着「删任务**不**清理 `task_tags`」，在 V1 之后这句已不准确。统一改为：

> 删任务时**不立即**清理 `task_tags`（为了让恢复任务的标签能自动接回，见 H1/H2）；
> 但在该任务被**永久删除**时（回收站裁剪 / 清空 / 单条永久删除 / 批量物理删除）同事务清理。
> ⇒ 孤儿行的生命周期从「永久」缩短为「0」，§7 的「孤儿数为 0」在运行期同样成立。

## V4 · H2 的成立条件（回应请示第 2 项）

H2「恢复任务后标签自动接回」**不是「技术上无法恢复」**，而是**有条件成立**，两个条件缺一不可：
1. **H1 成立**（恢复时写回原 id）→ 否则 `task_tags.task_id` 指向的 id 不存在，关联接不回；
2. **该条目仍在回收站里** → 被裁剪/清空意味着任务已永久删除，关联随之失效（见 V1 补充）。

所以规格里 H2 相关表述应从「无法恢复」改为「**在上述两个条件满足时自动恢复**」。

## V5 · G4b 的措辞（回应请示第 3 项）

采纳研究员建议：G4b **不按缺陷定级**，改写为**实现红线**——
它不是「要不要修」的问题，而是「实现时会不会踩」的问题。
且据研究员实测，RN 现有实现**已原值透传 `is_deducted`**（`recycleRepo.ts:263` / `:345` 均为 `row.is_deducted ?? 0`），
红线**当前未被触碰**。因此红线的作用从「提醒别踩」转为「**提醒后续改动者别破坏这个不变量**」。

# 追加裁决 · 第六轮（一个会静默损坏数据的陷阱）

## V6 · 🔴 `recycled_tasks.id` ≠ `task_id`，拿错会删掉**活任务**的标签关联

**这是我自己的措辞缺陷造成的**。我给实现者的工作项写的是「查出被裁剪的 id 列表 → 同事务删
`recycled_tasks` + 删这些 **id** 的 `task_tags`」，字面照做就是错的。

| 列 | 含义 |
|---|---|
| `recycled_tasks.id` | 回收站**自己**的自增主键 |
| `recycled_tasks.task_id` | **原任务的** `tasks.id` |
| `task_tags.task_id` | 关联的是**原任务 id** |

**金样本实测**（`recycled_tasks` 两行）：
```
id=1  task_id=5      ← 1 ≠ 5
id=2  task_id=99     ← 2 ≠ 99
```
而 `tasks` 表里 **id=1 和 id=2 都是活着的任务**。
按字面写 `DELETE FROM task_tags WHERE task_id IN (<recycled_tasks.id>)` 的实测后果：

| 做法 | 剩余 `task_tags` |
|---|---|
| 原始 | `(1,1) (2,2) (4,2) (8,999)` |
| ✅ 经 `task_id` 映射 | 不变（正确） |
| ❌ 拿 `recycled_tasks.id` 当 `task_id` | `(4,2) (8,999)` ← **活任务 1、2 的标签被误删** |

**裁定（写进实现工作项，单列一条）**——**三步，缺一不可**：

1. **条件用 `task_id`**，永远不用 `recycled_tasks.id`。
2. **`task_id` 必须取自「本次真正被永久删除的那几行」**，
   **不是「回收站里的所有行」**。
3. **被清掉的关联，其 `task_id` 对应的任务必须确实是已永久删除的**
   （否则那是**活任务**的关联，删了就永久丢标签）。

⚠️ **第 3 步是最容易漏的一步**：前两步都写对了，代码照样能删掉活任务的标签。
「写对也会误删」是**比「写错」更隐蔽的失败模式**——
`task_id` 用得完全正确、逻辑完全正确，但因为取的是**已裁剪条目**的 `task_id`，
而那个任务**已经被永久删除**（任务没了、它的标签关联也没了）→ 删掉的是**别人的**关联。
**所以「删哪些行」比「用哪个列」更要紧。**

**另外两条硬要求**：
- `permanentDelete` / `clearRecycleBin` 的语句**顺序不可调换**：必须**先删 `task_tags`**
  （子查询依赖 `recycled_tasks` 那行还在），再删 `recycled_tasks`。
- `clearRecycleBin` 的 `IN (SELECT task_id FROM recycled_tasks …)` **要带 `task_id IS NOT NULL`**
  （该列可空）。
- **单测必须用 `id ≠ task_id` 的数据**，并加**反向断言**：其他活任务的标签关联原样保留。
  否则错误实现同样会「通过」——这是本条最容易被单测放过的地方。

## V7 · `task_tags` 有**两类**孤儿，不要混

- **task_id 维度**：`task_tags.task_id` 在 `tasks` 与 `recycled_tasks` 中都找不到。
- **tag_id 维度**：`task_tags.tag_id` 指向已删除的标签（金样本实测存在 `8|999`，`tags` 里没有 999）。
  根因是**删标签的清理只覆盖新数据**，历史残留仍在。

`purgeOrphanTaskTags()` 的两个分支各自处理，**测试也要分别覆盖**——只测 task_id 维度会漏掉 tag 维度。

## 通则 1 · 任何断言必须有可复现的证据来源

- **单次 grep 命中不足以支撑「唯一调用方」「是死代码」这类断言**。
  必须反向搜索调用方所在文件的调用点，并确认没有第二处读取路径
  （同名方法、不同实现、不同入口）。
- **转述他人的结论必须自己复核**。本项目已发生：转述核查报告里的
  「符号名 / 文件名 / 依赖项」而未 grep，结果**三条全错**——
  符号不存在、文件不存在、依赖其实存在。
- **指出问题时必须能指到 `文件:行号` 或命令的真实输出**。指不出就是「没发现」，不能写成「已发现」。

## 通则 2 · 写完文档要逐条验证**文档内部的交叉引用**

代码事实错误会被人质疑（进而暴露），但**章节交叉引用错误不会被人质疑**——
没人会为一个章节号专门来提问，可它会让读者**查错地方**，同样是未经核实的断言。

自查时除了验证代码事实，**还要把文档里所有「见 §X.Y」的引用逐条验证**：
该章节必须存在、且内容确实与引用描述相关。本项目已发生 4 处这类错误
（指向不存在的 §6.7、指向「Flutter 特有能力」而非「既有行为」、两处同文档内自相矛盾）。

## 通则 3 · 只有「主动自查后自我修正」是可靠机制

本项目三次定级修正的触发方式不同，可靠性差别很大：

| 方式 | 案例 | 可靠性 |
|---|---|---|
| 被别人抓到 | P1-2 | 取决于有没有人恰好看到 |
| 被质疑后自查 | T1 | 依赖有人提出质疑 |
| **主动自查后自我修正** | G4b | **最高，不依赖外部注意力** |

前两种都会漏——没人质疑、也没人恰好看到的地方会静默留下错误。
⇒ **自查不能只查别人点到的位置**，要主动遍历自己写过的全部结论。

## 通则 4 · 「应该做的事」不能写成「已经做过的事」

把待办伪装成已完成的发现，是本项目出现过的**最严重错误形态**：
编造了一个 bug 与一个不存在的脚本，让他人去执行。
⇒ **「请执行 X」的指令发出前必须确认 X 确实存在**；
**「应该验证」只能写成待办计划，不能写成已通过的发现**。

## 通则 5 · 先问「这是 bug，还是有意分层的现状？」

这一条**比通则 1 更前置**——通则 1 讲的是「证据够不够」，这条讲的是「**问题定性的对不对**」。

本项目所有被修正的判断，**错误都出在定性环节，不是验证环节**：
死代码误判（把活代码当死的）、表格与数字矛盾（说 7 种列 9 行）、
定级三次修正（缺陷 → 中等 → 实现红线）、引用指向死代码、
「在 Flutter 侧成立」被当成「两侧都成立」。

**症状**：验证做得再细，**定性错了就是全错**——
把活代码当死代码，验证只会确认「确实没调用」，不会发现「我找错了地方」。

⇒ **任何「这里有问题」的判断，先问一句：这是缺陷，还是有意的分层/历史包袱？**
- 是缺陷 → 再问「它对用户有影响吗，影响是钱、是数据、还是体验？」
- 是分层 → 照搬，并在条目里注明「**照搬的是哪一侧、RN 侧是否仍成立**」。

本项目已多次因跳过这一步而误判：
一个「死代码」结论差点让数据导出功能消失；
一个「资金损失级」结论让所有人按一个不存在的行为去改代码。

## 通则 6 · 裁决推翻某个表述后，**按裁决编号** grep 受影响文档

这是一条**动作**，不是原则——所以它能真正约束行为。

**为什么它比通则 1–5 更可执行**：本项目被修正的文档问题，绝大多数不是「判断错」，
而是「**改了一处，没搜全文还有几处**」：

| 案例 | 残留数 |
|---|---|
| V1 改了 X3，没改 C.3 / D.3 / §6.2 f / §3.8 两处 / §7 | 6 处 |
| 4 处章节号导航错误 | 4 处 |
| §6.5 d 仍写「至今未裁决」 | 1 处 |

**⇒ 执行动作**：
1. **查文首的「裁决索引」表**（编号 → 受影响代码 → 受影响文档 → 落地状态），
   找到该裁决对应的**受影响文档**列表——**不要凭记忆判断「这裁决跟我有没有关系」**
   （裁决编号是客观的，文档归属是主观的；**按编号过不会漏，按记忆过会漏**）。
2. 对那几份文档 `grep -nE "<旧表述的关键字>"` **扫全文**，含表格单元格、行内注释、检查清单；
3. 命中处逐个判断：是需要同步、还是**刻意保留**（刻意保留的必须标「已作废」并写明理由，
   保留纠错链路比删掉更有价值）；
4. **同一份文档里出现两处口径相反的「照搬」是最危险的形态**——只读其中一处就会做错。
   本项目实际发生过（`spec-tasks.md` 的 §6.2 f 与 §6.0 X3 并存）。
5. ⚠️ **表格里的状态标注要回代码里数一遍，不采信标注本身；且读表格必须读完整行。**
   **实测（git 实证）**：索引表**建表时是 5 列**（`编号|主题|受影响代码|受影响文档|状态`），
   V6 标着 `✅（文档）`——而 V6 是**代码**裁决，单列写法让读者以为它已落地。
   software-engineer-1 抽查时发现这个不一致（**报告准确**）→ 拆成「文档 | 代码」两列，V6 变为 `✅ | ❌ 未落地`。
   ⚠️ **两个独立的错因，别混**：
   - **合成一列 → 二义性**（本项目的真因，已由拆列修复）；
   - **拿后来才做的修改倒推 → 误判**（两次，方向相反，见下表）。

   ⚠️ **同一个坑踩了两次、方向相反**（general-purpose-1 指出，比单写一次更有说服力）：
   两人**都读了拆列之后的 6 列版本**，都据此评价「拆列之前」的事：

   | | 读到的版本 | 结论 | 实际（git 可证） |
   |---|---|---|---|
   | software-engineer-1（**撤回**时） | 拆列**后** | 「原来就是两列，我误判了」 | 原来是一列，**他的报告准确** |
   | general-purpose-1（**更正**时） | 拆列**后** | 「原来不是合成一列，无需拆」 | 原来是一列，**拆列对症** |

   ⇒ **一个撤回正确发现，一个否定正确发现**——同一个动作、同一个方向。
   **⇒ 评价一件已经过去的事，必须先查时序，不能拿后来的状态倒推。**
   ⇒ **两条防护都要有**：
   (a) **同一裁决的状态不要在多处各存副本**——本项目曾有三份（索引表 / V8 盘点表 / 记忆文件），副本之间会冲突；
       **一个裁决的状态只存一处，其余位置引用它**。
   (b) **读表格/读命令输出必须读完整行**——**而且要连表头与图例一起读**，别拿半截下判断；
       **撤回一条结论前要先查时序**——别用「后来才做的修改」去否定「当时的发现」。
       ⚠️ **图例与单元格可能自相矛盾**：单列版的图例写「✅ 已落地」，而 V6 单元格写「✅（文档）」——
       **只看单元格不看同列的图例，就会把「文档已写」读成「已落地」**。
       **这才是本项目误判的真因**（不是「grep 截断了输出」——那个说法是未经验证的假设，见下方「起了头 vs 跟随」）。

## 通则 7 · 改文档前**先查 git**，只认工作区不认记忆

> 「你读的是旧版」这句话本身可能就是错的。**先查 git，再下结论。**

本项目实际发生过：我在给同事的回复里写「V2 前提那条其实已经落地了、你读的是旧版」，
而事实是**那条是他先发现的、我随后才改的**——他的发现完全有效，
是我的归因写错了。**「已经落地」与「有人先发现」是两件事。**

**⇒ 默认手段：三查合用**（software-engineer-1 / general-purpose-1 连续两轮具体化的结果）

| 查什么 | 命令 | 能回答 / 不能回答 |
|---|---|---|
| **哪笔引入的** | `git log -S'<字符串>' -- <文件>` | ✅ 定位引入提交<br>❌ **不能**回答「报告那一刻它在不在」 |
| **某个时点的内容快照** | `git show <commit>:<文件> \| grep -c '<字符串>'` | ✅ 回答「那一刻有几处」 |
| **纯新增还是改写** | `git show <commit> -- <文件> \| grep -cE '^-[^-]'` | ✅ 0 个删除行 = **纯新增**（不是改写既有文字） |

⚠️ **关键区分：「引入提交」≠「报告时刻的状态」。**
`git log -S` 找到 48ccdff 只说明**那笔是引入点**；要判断「报它的人在报告时看到的是什么」，
必须查**内容快照**（`d3e2326`=0 / `3e46cda`=0 / `48ccdff`=1）。
**本项目就栽在这里**：software-engineer-1 只查了 ①（找到引入提交 = 48ccdff），
就以为「已落地 ⇒ 他读的是旧版」——**漏了 ②**（报告时刻那处根本还不存在）。

⚠️ **归因错误比文档陈旧严重得多**：文档旧只是信息不准，
而归因错误会**把别人的有效发现说成是他记错了**——那是**对人评价的扭曲**。

⚠️ **一个 `git log -S` 覆盖不了的区分**：「独立复现」与「重复报告旧结论」在信号上很像，但含义相反。
本项目里 §3.8 的 V2 前提被**两人分别报上来**（general-purpose-1 与 software-engineer-1），
第二个人报的不是「读旧版」而是**独立复现**。
区分仍靠 ②：**若那条内容是在我回应之后才被加进文件的，报它的人就是原始发现者。**

⚠️ **第三维：不是「要读全」，而是「要读对方当时读的那一版」。**
① 查「哪笔引入」、② 查「某个提交的内容快照」，**都还没回答「他当时眼前是什么」**——
他看的是**工作区**，可能是**未提交**的中间状态，与任何提交都不对应。
**「读完整行」解决信息完整性，「锁定版本」解决参照系正确性——后者错了，前者做得再对也没用。**

本项目实际踩到**两次、方向相反**：
- 一人用**修复后**的版本否认自己**修复前**的质疑；
- 另一人用**修复后**的版本否认**修复前**的标注。
**两次都是「都在看 git、都看到了事实、都不是对方面对的事实」。**

⇒ **回答「他当时看到什么」只能用 `git show <他报告之前的提交>:<文件>`，不能拿当前版本代替。**

⚠️ **「读全」这条防护防不了这种错。** 本项目同一通则被同一人在同一天撞了两次：
一次用修复前的版本否定正确质疑，一次用修复前的版本把**已修好的**当待办。
**两次都读得很全**（整行、完整上下文），**但参照系错了**。
⇒ **判断「某处是否已修好」时，先看最新提交时间，再看内容**：

```bash
git log --format=%ad --date=format:%H:%M:%S -3 -- <文件>   # 最新几次提交的时刻
git show <最新提交>:<文件> | grep '<关键字>'                  # 那时到底有没有
```

**「内容对不对」与「内容是不是最新的」是两个问题**，混起来就会用旧内容否掉新结论。

⚠️ **一个容易被忽略的失效场景：一个人起了头，另一个人跟随。**
本项目最后一轮，某个因果解释（「读取时截断了输出」）**由一人先提出且未经验证**，
另一人顺着它解释了自己的误读——**于是看起来像两次独立验证，其实是一个未验证假设被复述**。
而且**被归因者本人澄清：他从未用过那种命令**（他用的是整行输出），
「截断」是别人先编的说法、他后来复述了它。

**⇒ 「防两人独立犯错」的防护，对「一个人起了头、另一个人跟随」是无效的**——
因为跟随者会以为自己在独立判断。
**⇒ 凡是要写进通则的因果，必须能指出「谁验过、怎么验的」；没验过的因果只能写成假设。**

⚠️ **撤回的不对称性：撤回应别人，比维持自己的错误更危险。**
本项目实际发生：一方**撤回了自己那条准确报告**（依据是拆列后的版本），
另一方**要求更正一条正确数据**（同样依据拆列后的版本）。
**两次都是拿「我后来看到的状态」去否定「别人当时看到的状态」。**

为什么撤回更危险：
- **维持错误** → 错误只影响那一件事；
- **撤回正确发现** → 那条发现**从记录里消失**，且**没人会再去发现一次**，
  而「已经被撤回」这个状态会**阻止别人重新提出**它。
本项目就差点这样：若采信那次撤回，「V6 曾是单列」这个事实会从记录里消失，
而它恰恰是「拆列」这个动作存在的理由。

⇒ **撤回应对方结论前，必须先查时序**（`git log -S` + 内容快照 + 锁定对方当时的版本），
**并且要意识到：撤回是不对称的**——它不只是「改口」，而是在删掉一个已经被验证过的发现。
⚠️ **主动动作 vs 被动核实：两者的错误率完全不同**（general-purpose-1 的收尾观察，最有操作性的一条）。

本项目最后一轮，一个成员的全部失误**集中在「主动发起的动作」**上——
要求更正一条正确数据、编造一个未验证的因果去支撑它、要求撤回三条其实已被裁决的待办；
而他**被动核实别人的结论时准确率很高**（V6 第 3 步、第三份状态副本、文档内两处矛盾，都是他读出来的）。

| | 动作 | 需要的前置 |
|---|---|---|
| **主动动作** | 要求更正、要求撤回、发指令、给裁决 | **发起前先查时序**（对方面对的是哪个版本） |
| **被动核实** | 读代码、读文档、核对标注 | **只需读准当前状态** |

**⇒ 为什么这条比通则更好用：它不依赖记性。**
「记得更全 / 查得更细」这类要求靠自觉；而「**主动动作前必须先查时序**」有一个**固定触发点**——
每一次发起动作之前。**把检查挂在触发点上，而不是挂在「记得」上。**

⚠️ **③ 最隐蔽的形态：把他人给出的因果当成自己查证的结论。**
本项目发生过：一人先编了一个**未验证**的原因（「读取时截断了输出」），
另一人**复述成自己的误判理由**——听起来像「我独立地误判了」，
实际是「**我放弃了自己查过的证据、采信了一个未验证的假设**」。
⇒ **不采信任何转述——包括他人给出的因果，也包括自己上一轮的说法。**

## 通则 9 · 断言必须**成对**：一正一反，缺一不可

> **「该有的还在」和「不该有的没了」必须同时断言。**
> 只断言「结果符合预期」的验收，**看不见「不该发生的事发生了」**。

本项目一天内栽在同一个坑两次：
1. `verify_orphan_cleanup.py` 第一版：四个场景串行跑在同一个库上，场景 1 清空后 2/3 被**静默跳过**，
   却仍报「✅ 通过」；
2. 同一脚本第二版：只断言「孤儿数 = 0」，
   而**误删活任务的标签关联不产生孤儿**（它本来就该存在，只是不该被删），
   只会让孤儿数更接近 0 ⇒ **断言越绿越危险**。实测：跑完仍 exit 0，但活任务 5 的标签已被静默删掉
   （software-engineer-1 发现）。

**⇒ 落地要求**
- 每条验收路径都要有**反向断言**：跑完之后，**本该保留的东西必须原样还在**；
- 断言工具**必须做负向测试**：故意破坏实现 → 断言必须报错且退出码非 0。
  **没做过负向测试的断言，不算断言。**
- 场景**被跳过 ≠ 通过**。跳过要显式判失败。

## 通则 8 · 提交前**跑脚本**核对 Markdown 渲染，不只看源码

Markdown 的**渲染结果**与**源码**是两回事。本项目实际发生过：我加的
callout 后面缺一个空行，导致**后面那句话被吞进引用块**——

```

python tool/check_md_blocks.py <文件>      # 检查指定文件
```

它检查三类问题：① 引用块吞段落；② 代码围栏未闭合（``` 数量为奇数）；
③ 引用块后紧跟列表行。**发现问题时退出码为 1**，可直接挂 pre-commit。

**这个脚本当场清出了 8 处存量问题**（全在 `tool/ROADMAP.md` 的版本卡片里，
`> **北极星贡献**：…` 后面直接跟 `- [ ]` 列表行）——
**那些是本项目早期重写路线图时留下的，一直没人发现，因为没人用渲染视图看。**

⚠️ **这类问题只影响「读者看到什么」，不影响「文件里有什么」**——
所以 `git diff` 永远发现不了它，必须用渲染后的视图或本脚本。

⚠️ **归属要说清**：§3.8 那个渲染 bug 是**我引入的**（我加 callout 时漏了空行），

## V9 · 状态层方案：**Zustand**，在写界面代码之前定下来

研究员指出 Flutter 侧是硬编码装配（`main.dart` 的 `MultiProvider` 显式列 11 个 Provider、
`app_router.dart` 有 14 条模块页直引），并问「RN 侧要不要直接引 React Navigation」。
这确实是缺口，但**要分清它影响什么**：

| 层 | 是否受状态层方案影响 |
|---|---|
| 仓储层（`repo/*.ts`） | ❌ **不受影响**，纯数据访问、与 UI 无关 → `taskRepo.ts` 可以直接开工 |
| 界面层（M1 的页面） | ✅ **受影响**，开工前必须定 |

**裁定**
- **状态层用 Zustand**。理由：轻量（无 Provider 嵌套与重渲染传播问题）、与 React 19 兼容、
  且**仓储层返回的是同步数据**（`executeSync`），store 直接持有即可，不需要额外的异步层。
- **导航不引 React Navigation**。M1 只需要「底部 Tab + 少量模态」，
  手写一个约 150 行的栈式导航器更可控；等 M2/M3 出现真正的多级返回与手势需求再评估。
  ⚠️ 理由要写清：不是否定 React Navigation，而是**当前需求用不上它那 90% 的能力**，
  而引入它会带来 3 个原生依赖（screens / gesture-handler / reanimated）与构建风险。
- 界面层开工前，先出一份「状态 → 组件」的映射表（哪个 store、哪些页面消费），避免再次出现
  Flutter 侧那种「14 条直引」的硬编码耦合。

**裁定：所有裁决条目必须带一个明确标记**

| 标记 | 含义 | 例子 |
|---|---|---|
| **【照搬】** | 与 Flutter 行为完全一致，不要改 | 回收站上限 10 条、仓库按 name 分组、`loop_id` 保留 |
| **【修复】** | 明确偏离 Flutter，原因写在条目里 | H1 恢复写回原 id、V1 永久删除时清关联、T4 逾期口径 |
| **【有意偏离】** | 行为不同但等效或更优，理由已给 | 排序加 `id` tiebreaker、删不可达空态分支 |

**并且文档里凡出现「照搬」二字，必须同时写明它在 RN 侧是否仍然成立**（研究员建议，我合并进本条）：

| 情况 | 写法 |
|---|---|
| RN 侧与 Flutter 一致 | **【照搬】** + 一句「RN 侧同样不清理，理由：…」 |
| Flutter 不清理、**RN 要清理** | **【修复】** + 写明「**Flutter 现状 = 不清理；RN 决策 = 清理**」 |

**任何人只读到其中一处都会做错**。
根因是「在 Flutter 侧成立」被当成了「两侧都成立」——
这与通则第 4 条（「应该做的事」不能写成「已经做过的事」）是同一类错误。

## V14 · 搜索并入列表数据流 —— 内部实现变更，**用户可见行为不变**

Flutter 侧任务列表是**两套结果**：主列表走 `getTasksForDate` + 过滤，
菜单里的搜索走**独立的第二套查询**（`searchTasks`），两者互不影响——
所以搜索结果与列表的排序规则可能不一致，且主列表的「未找到匹配」空态分支**永不可达**。

RN 侧**并入单一数据流**（列表 + 过滤 + 搜索统一在一个查询里）。
⚠️ **必须保证用户可见行为不变**，具体三条：
1. 排序规则在「有搜索词」与「无搜索词」时**保持一致**；
2. 搜索结果**同样受标签/状态筛选约束**（不是搜索就绕过筛选）；
3. 搜索无结果时的空态**要真的能出现**（Flutter 侧那个不可达分支是缺陷，RN 侧要可达）。

**这是内部实现简化，不是功能删减**——搜索能力保留且更一致。

`purgeOrphanTaskTags()` 的两个分支各自处理，**测试也要分别覆盖**——只测 task_id 维度会漏掉 tag 维度。

# 追加裁决 · 第四轮（修正 T1，并补两条）

## U1 · T1 的「同步修正 4 处引用」是**多余的**，改为条件式 ⚠️**修正上一条裁决**

原裁决要求「恢复时同步修正 `task_tags.task_id` / `points_records.related_id` / `pomodoro_records.related_task_id`」。
**这个要求是错的，而且照做有害。**

**理由**：保留原 id 之后，**所有以该 id 为键的引用自动重新变成有效**——
`task_tags` 里那些「孤儿」行从来没被删过（删任务本来就不清 `task_tags`），
它们指向的 id 一旦重新出现在 `tasks` 里，关联**自动接回**。
再去 `UPDATE ... SET task_id = 7 WHERE task_id = 7` 属于**空操作**；
若实现时误写成别的条件，反而会把本来正确的引用改错。

**修正后的裁定**
- **正常路径（`task_id` 非空且 `tasks` 中无冲突）**：保留原 id，**不做任何引用改写**。
  标签关联自动恢复，积分幂等自动生效。
- **仅当主键冲突、降级为新 id 时**：才改写 4 处引用（`points_records` 的三个 type +
  `pomodoro_records.related_task_id` + `task_tags.task_id`）。
- **`task_id IS NULL` 的历史数据**：无法映射，直接自增插入，**不改写任何引用**，并打一条警告日志。
  这是唯一残留的不一致场景，属可接受的极少数脏数据。

**判断依据**：QA 指出「复合键归并 `_insertIfNotExistsTxn` 首行就 return，`_generateDates` 从不被调用，
所以从未有实例真正插入」——意味着这些「已生成实例」在现实里是 0 条。修复存在**回归风险**。
M1 的原则是「照搬为主、修 bug 为辅」，而「模板扣分时已完成实例是否补扣」**不是 bug 而是未定义行为**。
→ **裁定：M1 照搬**（实例行 `is_ok=0, is_deducted=0`），在代码注释写明未定义行为，留 v6.x 决策。

## U2 · 「仅恢复当天」恢复出的 `loop_id` —— **照搬保留**，已验证无害

Flutter 现状：把 `recurrence` 改成 `'none'` 但**保留 `loop_id`**，产生「`recurrence='none'` 且 `loop_id` 非空」的组合。
按「照搬为主」原则应保留，但需确认它是否会污染循环生成。

**核实结论**：`getRecurringTasks()`（`task_repository.dart:236-243`）的 `WHERE recurrence != 'none'`
决定了 `loop_id` 非空但 `recurrence='none'` 的行**永远不会被循环生成器取到**。

→ **裁定：照搬保留 `loop_id`**，零行为变更。若将来要清空，属于独立的行为变更，不在 M1。

## U3 · X3（删任务不清 `task_tags`）与 H4（孤儿清理）**不冲突**——已由 T2 解决

研究员报告 X3 与 H4 冲突，**实际不冲突**，因为 T2 已裁定 `purgeOrphanTaskTags()` **不在启动时自动执行**
（只在「回收站清空」或「M2 手动入口」触发）。所以：
- 正常运行时 `task_tags` 行数不变 → §7 第 1 条「迁移前后完全一致」守得住；
- 迁移时点没有执行过 purge → §7 第 3 条「孤儿为 0」也守得住。
- 真实库实测孤儿为 0，两条都验证通过。

## U4 · `schema-v3.md` §7 第 3 条的 SQL 口径要改（不是改判定，是改定义）

QA 指出原验收 SQL 会**误判**：它只 `LEFT JOIN tasks`，而**回收站里的任务在 `tasks` 中没有对应行**，
于是「回收站任务的标签关联」会被算成孤儿 → 真实库当前为 0，但一旦用户删过任务就必然非 0。

**裁定**：§7 第 3 条的孤儿定义改为「在 `tasks` **与** `recycled_tasks` 中都找不到的 `task_id`」——
这与 H4 的 `purgeOrphanTaskTags()` 采用**同一定义**，避免两处口径分叉：

```sql
-- 3) 孤儿关联（应为 0；回收站里的任务不算孤儿）
SELECT COUNT(*) FROM task_tags tt
  LEFT JOIN tasks t ON t.id = tt.task_id
  LEFT JOIN recycled_tasks r ON r.task_id = tt.task_id
 WHERE t.id IS NULL AND r.id IS NULL;
SELECT COUNT(*) FROM task_tags tt
  LEFT JOIN tags g ON g.id = tt.tag_id WHERE g.id IS NULL;
```

§7 的**判定标准不变**（仍要求为 0），只改这条 SQL 的定义，并在 §7 末尾加时序说明：
「本节在迁移完成时立即执行；运行期的孤儿清理不参与本验收」。
