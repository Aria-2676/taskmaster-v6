# 验收与交付说明

> 最后更新：2026-11-01

## 什么时候用

- 一个功能/修复准备交付，需要给用户“照着验”的清单
- 用户说“验收/检查一下/能不能用”
- 发版前确认本轮验了什么、没验什么

## 步骤

1. **先分类**：每条验收项属于哪一层？
   - 机器判定：数据落库、字段显隐、导航、文案存在、排序、状态迁移、插件安装/升级
   - 人判定：手感、观感、产品取舍、跨设备/权限/后台/通知
2. **能自动化的先写测试**。不要把“我自己跑一下就知道”的条目丢给用户。
3. **写清单**：`docs/acceptance/<日期>-<主题>.md`，按
   `docs/conventions/acceptance-template.md` 的两层结构。
4. **每条四件套**：编号 / 路径 / 操作 / 可观察预期 + 排查线索。
   - 一步一编号；数量写死；失败能定位到文件/状态。
   - 禁止“正常”“流畅”“符合预期”。
5. **人判定条目 ≤10 条**；超了拆批次。
6. **回归组**：至少 3 条上一轮验过的关键路径（D 组）。
7. **真机项**：单独标“需真机”；交付说明写“未在真机跑过”或“已跑（机型/系统）”。
8. **自测证据**：测试名 + 通过；总数对比上一轮（只增不减）。
9. **已知未做/限制**：写清楚，不要藏。
10. **签收**：用户逐条勾；不过的编号回到实现；**未签收不推送**。

## 清单骨架

```markdown
# 验收 · <主题>（<日期>）

> 对应提交：`<sha>` ｜ 环境：`flutter run -t lib/main_v6_preview.dart`
> 结论：未验收 / 通过 / 部分不过（不过的编号：　）

## 零、已自测（机器判定）
| # | 断言 | 证据 |

## 一、需要你判断（≤10 条）
| # | 路径 | 操作 | 预期 | 不过时先看 |

## 二、已知未做 / 已知限制
```

## 硬规则

- 没有验收清单，不要说“做完了”。
- 用户要动手的条目 ≤10；能测试的转成测试。
- 手感/平台层只能真机判断；测试只锁“有没有这个特征”。
- 不可复现 bug 不写“已修复”，写“机制证明 + 保险 + 仍未验证”。
- 场景被跳过 = 失败；测试被删除要说明理由。
- 验收数字必须与真实运行一致，不估算。

## 输出

- `docs/acceptance/<日期>-<主题>.md`
- 回复里的摘要（编号 + 不过时先看哪）
- 明确的“未验证项”
