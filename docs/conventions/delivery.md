# 交付流程与发布纪律

> 最后更新：2026-11-01

这套流程的每一条都来自一次真实损失，不是流程洁癖。**没有验收清单，就不要说“做完了”。**

## 1. 标准流程

```
① 定案 → ② 实现 → ③ 自检 → ④ 验收清单 → ⑤ 用户签收 → ⑥ 提交/推送
```

- **① 定案**：把方案、代价、放弃的选项说清楚。方案被推翻时，把作废原因写进
  `docs/decisions.md`，别让下一轮重新发明。
- **② 实现**：先跑通再美化；一次只推进一个可验收的切片。不要边做边扩大范围。
- **③ 自检**：见 §3，一项都不许跳。
- **④ 验收清单**：见 §2，这是进入 ⑤ 的唯一凭证。
- **⑤ 签收**：用户按编号逐条勾，明确指出哪条不过。
- **⑥ 提交/推送**：见 §4。

## 2. 验收清单

写进 `docs/acceptance/<日期>-<主题>.md`，同时在回复里给摘要。模板见
`docs/conventions/acceptance-template.md`。

### 先分层，别把用户当测试机

| 类型 | 谁验 | 证据怎么给 |
|---|---|---|
| 数据落库、字段显隐、导航跳转、文案存在、排序、状态迁移 | 实现者/核查者 | 写成自动化测试；清单只列“编号 + 测试名 + 通过” |
| 真机手感（滚动、键盘、动画、拖拽、弹层热区） | 用户 | 编号 + 一步操作 + 可观察动作，标“需真机” |
| 视觉/文案偏好 | 用户 | 截图或一句话 |
| 跨设备、权限、后台、通知 | 用户 | 机型 + 步骤 |

- **用户要动手的条目控制在 10 条以内**，超了先拆批次。
- 交付前逐条自问：**这条能不能用测试断言？** 能 → 去写测试，别写进清单。
- 环境里没有设备时，先问“有没有设备 / 要不要我跑”，不要默认把用户当测试机。
- “已自测”一节保留编号和证据，用户想抽查可直接对照。

每条必须四件套：

| 字段 | 要求 |
|---|---|
| 编号 | `A1` `B3`，稳定可引用（用户会说“B3 不过”） |
| 路径 | 从冷启动开始写全：设置 → 我的 → 外观 → … |
| 操作 | 一个动作。要两步就拆两条 |
| 预期 | **可观察**：出现的文字、数量、颜色、字符。禁止“正常”“流畅”“符合预期” |

外加一列**排查线索**：这条不过，最可能是哪个文件/哪个状态。

分组建议：`A 新增功能` / `B 交互手感` / `C 数据安全` / `D 回归`。
**D 组必须有** —— 改编辑页弄坏“左滑删除”这类事故一次就够。

手感类只能真机判断，测试锁不住；交付说明必须诚实写“没在真机跑过”，
不许拿“测试全过”顶替。

## 3. 自检清单（进入 ④ 之前逐项过）

- [ ] `flutter analyze lib` 无 error（info/warning 看一眼，不新增）
- [ ] 全量 `flutter test` 通过，记下总数（对比上一轮，只增不减）
- [ ] 新增逻辑有测试：断言**行为**，不是“跑了一遍”
- [ ] 数据库改动有迁移测试（造真老库再打开）
- [ ] 修 bug 有反向测试：改回旧实现会红
- [ ] 该写的文档写了：`docs/INDEX.md` 唯一源、`docs/decisions.md` 记取舍
- [ ] 明确列出**本轮没验证的东西**（真机手感、未复现 bug、跳过的平台）
- [ ] 验收清单每条都问过“能不能自动化”，能的一律转成测试
- [ ] `git status` 干净，除了有意为之；没有敏感文件

### 四条红线

1. **未验收不推送。** 用户没说“过了/可以了”，就不 `push`。本地 `commit` 可以做。
2. **带问号 = 在征求意见，不是下指令。** 用户消息有“吗/？/是不是/能不能”时，
   先给判断和取舍，等定案再动手。
3. **批量替换/脚本改配置，必须验证结果。** 脚本 `assert` 匹配数，改完 `grep` 复核；
   配置类改动必须有测试或 build 兜底。
4. **不可复现的 bug 不算修好。** 要么给出机制层面的因果证明，要么加一层
   “即使原因仍在也兜得住”的保险，且这层保险必须能被自动化测试覆盖。
   “再试一次没出现”不是验收标准。

## 4. 提交与推送

**提交和推送是两件事**（用户 2026-10-28 定案）：

| 动作 | 什么时候 | 目的 |
|---|---|---|
| 提交（本地） | 一个可独立回退的小步做完、**且验证过** | 改坏了能小步退回去 |
| 推送 | 攒够一件完整的事 + 用户签收 | 仓库历史整洁易读 |

- 提交前必须先验证：`flutter analyze lib` 无 error + 全量测试通过。验证不过就不提交。
- 提交信息写**为什么**，不是“改了哪些文件”。
- **推送前合并**：把攒下的多个提交合成 1 个（改动大且主题不同，就按主题合成少数几个）。
  历史可读性靠这一步，不靠提交时的克制。
- 推送用 `tool/push_via_api.ps1`（本网络 `git push` 被限速到 <1KB/s）。
  该脚本只做**单提交快进**，并把时间戳归一化成 UTC 导致 sha 变化；
  **合并成单提交后这两条都不再是问题**。
- 推送前再确认一次：用户签收了吗？
- 推完补 `git update-ref refs/remotes/origin/main <sha>`，否则 `git status` 会一直显示 ahead。

## 5. 发版

### App 版本

1. `pubspec.yaml` 的 `version` 抬 build 号（`6.x.y+6001`…），versionCode 只能涨。
2. 构建 + 验签（确认签名是仓库外那把 keystore）。
3. 先传包到 GitHub Release / Gitee Release，回读 size + digest 核对。
4. **最后**改 `update.json`（`latest.version` + downloads 的 url/sha256/sizeBytes/mirrors）。
5. 刷 jsDelivr 缓存；知道 gcore 可能刷不掉，客户端按 `updatedAt` 取最新。

**顺序不能反**：清单先改、包没传，用户点更新会拿到死链，而且不会点第二次。
`downloads` 留空是安全中间态（客户端判定“无更新”，不报错）。

### 插件版本

1. 改 `plugins/src/<id>/plugin.json` 的 `version`。
2. `python tool/make_demo_plugin.py` 打包 + 重算索引 sha/size（版本号从 manifest 来，不手写）。
3. 决定随包还是只走仓库：默认走仓库；只有“断网必须可用且没它 App 不能用”才随包。
4. 提交并推送；刷 jsDelivr 缓存。
5. 用户在插件市场刷新即可看到/升级，**不需要发 App 版本**。

**打包必须幂等**：同内容重打包不能改字节；否则索引 sha 与线上文件对不上，表现像网络问题。

### 被引用的版本冻结

V5/V6 引流入口里写死的版本 + sha 是**永久目标**：一旦发布，字节不能再变。
要改指向就发下一个版本，不要重发旧包。

## 6. 环境与命令

```bash
# 静态检查
flutter analyze lib

# 全量测试（代理会劫持回环 WebSocket，必须先清）
env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy -u ALL_PROXY -u all_proxy \
    NO_PROXY=127.0.0.1,localhost flutter test

# 预览入口（写演示数据、不联网）
flutter run -t lib/main_v6_preview.dart -d emulator-5554
```

- `WebSocketException: Invalid WebSocket upgrade request` = 代理没清，不是代码问题。
- `CreatePipe ERROR_PIPE_BUSY` 是另一个偶发环境问题，别混为一谈。
- 模拟器命令统一加设备序列号；`adb` 截图坐标先 `uiautomator dump` 拿 bounds，别按比例估。
- 真机装 release 包前先 `adb uninstall`（debug/release 签名不同会 `UPDATE_INCOMPATIBLE`）。

## 7. 上下文被压缩之后

先读这四处，再动手，不要凭印象接着写：

1. `docs/ai/README.md` —— 开工顺序与任务路由
2. `docs/INDEX.md` —— 文档地图 + 已证伪断言
3. `docs/decisions.md` —— 为什么这么做
4. 当前任务文件 `docs/ai/work/<日期>-<主题>.md` —— 上一轮做到哪、下一步

## 8. 交付物

交付物 = **代码 + 可量化验收清单 + 明确未验证项**。
不是“我改完了”，也不是“测试全过”。用户签收的是清单，不是你的自信。
